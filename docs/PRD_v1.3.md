## 1. 产品概述

### 1.1 产品定位

深圳钓鱼助手是一款面向深圳本地钓鱼爱好者的工具型应用，聚焦「找钓点 + 查鱼情 + 周边配套 + 一键导航」。产品不做内容社区，也不做电商闭环，优先解决三个决策问题：

- 不知道去哪钓：钓点信息分散在贴吧、微信群、短视频，缺少结构化、可检索的集中入口。
- 不知道能不能钓：禁钓、限钓、收费信息不透明，新手容易白跑。
- 到了现场心里没底：不了解鱼种、收费、停车、餐饮、厕所等配套。

一句话价值主张：把深圳的钓点查清楚、导航到、钓得明白。

### 1.2 目标用户


| 用户分层      | 画像特征                   | 核心诉求             | 占比预估  |
| --------- | ---------------------- | ---------------- | ----- |
| 新手入门者     | 刚接触钓鱼，怕空军，怕踩雷，以台钓、手竿为主 | 明确能不能钓、怎么去、附近有什么 | 约 40% |
| 周末休闲钓友    | 家庭或朋友结伴出行，关注配套与舒适度     | 停车、餐饮、厕所、亲子设施    | 约 35% |
| 资深野钓与路亚玩家 | 追求具体鱼种、水质、钓法适配         | 鱼种详情、钓位特征、钓法建议   | 约 25% |


### 1.3 核心场景与 V1.0 覆盖


| 场景         | 描述                      | V1.0 覆盖 | 说明                                     |
| ---------- | ----------------------- | ------- | -------------------------------------- |
| 场景 A：周末去哪钓 | 按区域、鱼种、收费筛选钓点，查看详情后导航前往 | 完整覆盖    | 主场景，也是首版核心链路                           |
| 场景 B：到了现场  | 查看是否开钓、水位、鱼口、收费变动       | 部分覆盖    | V1.0 展示最近核实时间与开放状态；实时情报由 V1.1 的 UGC 承接 |
| 场景 C：顺路找配套 | 查看钓点周边餐饮、停车、补给、休闲场所     | 完整覆盖    | 依赖 POI 数据，按距离排序                        |


V1.0 的产品承诺应收敛为「查得到、看得清、导得走」；不要在上线宣传中承诺实时鱼情。

### 1.4 产品价值与差异化


| 维度    | 现状痛点        | 本产品价值            |
| ----- | ----------- | ---------------- |
| 信息集中度 | 钓点信息零散，无结构化 | 结构化钓点库，一屏看清关键字段  |
| 决策效率  | 依赖口碑与猜测     | 多维筛选、详情页、导航一键打通  |
| 风险规避  | 禁钓与收费信息滞后   | 标注开放状态、收费状态与核实时间 |
| 出行体验  | 周边信息需另查     | 周边配套与导航在同一链路内    |


### 1.5 产品边界与反目标

以下内容明确不做，避免开发中途扩张范围：

- 不做内容信息流、关注、私信、评论楼中楼。
- 不做电商、交易、钓场预订、钓具销售。
- 不做自建地图或自建导航引擎。
- V1.0 不做多城市、天气、潮汐、评分体系、用户账号体系。
- 不推荐明确禁钓的水域；禁钓点只做风险提示，不提供导航去钓鱼的入口。

### 1.6 成功标准

- 用户能在一次会话内完成「筛选、查看详情、发起导航」。
- 上线时具备 100 个可查询的深圳钓点，其中核心钓点不少于 50 个。
- 详情页信息足以支撑「去不去、怎么去、附近有什么」三个判断。
- 量化指标见第 11 章。

## 3. 信息字段与数据模型

### 3.1 实体关系

```text
spot 1 --- N spot_poi N --- 1 poi
spot 1 --- N report N --- 1 user          （V1.1）
user 1 --- N favorite N --- 1 spot        （V1.1）
user 1 --- N footprint N --- 1 spot       （V1.1）
report 1 --- N report_like N --- 1 user   （V1.1）
report 1 --- N report_abuse N --- 1 user  （V1.1）
admin_user 1 --- N audit_log
spot 1 --- N import_job                    （导入任务关联）
```

数据模型原则：

- 数据库与接口字段统一使用 snake_case。
- 主键统一使用 26 位 ULID 字符串，避免自增 ID 暴露数据量。
- 所有业务表带 `created_at`、`updated_at`、`deleted_at`；删除采用软删除。
- 坐标统一存储 GCJ-02；数据库使用 `decimal(9,6)` 分别存纬度和经度。
- POI 与钓点的距离是关系属性，存在 `spot_poi`，不放在 POI 表。
- 钓点、内容、用户都有明确状态机；对外只展示已发布状态。

约束与规则：

- 唯一约束 `(provider, provider_uid)`；同一用户同一 provider 只保留一条主身份。

- 账号注销：软删除 user，匿名化昵称与头像，删除 user_identity，保留必要审计记录；7 天内完成。
- 同一自然人多身份合并由运营后台人工处理，合并记录写入审计日志。

- 纬度范围 22.3 至 22.9，经度范围 113.7 至 114.7；超出范围拒绝保存。
- 已发布钓点：`spot_name`、`district`、坐标、`address`、`fish_types`、`fee_status`、`water_type`、`venue_type`、`open_status`、`verified_at` 必填。
- 核心钓点发布时至少 1 张图片；周边场所数量在发布门槛检查，不作为单点发布拦截。
- 禁钓点必须填写 `ban_note`。
- 图片最多 9 张，单张上传不超过 5 MB，格式 JPG 或 PNG；服务端压缩到 300 KB 以内。
- 重复钓点判定：同区域、名称相似、坐标距离小于 200 米，保存时告警，由运营确认。
- `spot_poi` 同一钓点与同一场所只能有一条关系。
- 所有软删除记录默认不参与查询。

#### 4.3.1 首页列表

#### 4.3.2 首页地图

- 地图组件铺满内容区，顶部悬浮搜索与筛选，底部按需弹出卡片。

- 性能：V1.0 最多 500 个点位，100 个点位下聚合与拖动流畅。

- 入口：首页顶部搜索框。
- 范围：钓点名称中文模糊匹配，不搜索地址与周边场所。

- 结果：复用列表卡片，展示结果数。
- 空结果：没有找到相关钓点，换个关键词试试。

- V1.0 不做搜索历史与拼音搜索。

- 形式：底部弹层。
- 区域：单选。

页面分区从上到下：

1. 图片轮播：最多 9 张，点击可预览大图；无图时展示占位图。

## 5. 地图与导航方案

### 5.1 结论

小程序内可以完成地图预览与导航。参考租房类小程序的做法：页面内用地图组件展示点位和底部卡片，点击导航后进入微信原生地图页，由用户发起导航。产品不自建导航引擎，也不在 V1.0 做三地图选择。

产品定位为信息查询工具，不提供路线规划或导航服务本身；地图组件只用于点位预览，导航由微信原生地图页完成。若微信审核认为地图 Tab 属于地图或导航服务，按 7.8 的降级方案移除地图 Tab，保留详情页预览与 `wx.openLocation`。

V1.0 导航目标体验：

- 首页地图：查看钓点分布，点击点位查看卡片。
- 详情页：地图预览点位，点击导航。
- 微信地图页：展示目的地名称、地址、坐标，用户可选择开始导航。
- 失败兜底：复制地址，用户可粘贴到任意地图 App。

### 5.2 实现基线


| 场景    | 实现               | 关键 API 或组件                               | 说明                     |
| ----- | ---------------- | ---------------------------------------- | ---------------------- |
| 首页地图  | 小程序原生地图组件，标记点与聚合 | `<map>`、`MapContext`、`initMarkerCluster` | 基础库 2.30.0 及以上         |
| 详情页预览 | 原生地图组件，单标记       | `<map>`                                  | 高度 180 像素，底部展示导航按钮     |
| 发起导航  | 打开微信原生地图页        | `wx.openLocation`                        | 传 GCJ-02 坐标、名称、地址、缩放级别 |
| 用户定位  | 获取用户位置           | `wx.getLocation({ type: 'gcj02' })`      | 按需请求，不自动弹窗             |
| 复制地址  | 复制到剪贴板           | `wx.setClipboardData`                    | 导航失败兜底                 |
| 三地图增强 | 跳转地图小程序          | `wx.navigateToMiniProgram`               | V1.1 预研，需要 AppId 与路径   |


实现要点：

- `wx.openLocation` 打开的是微信内置地图页，用户可在页面内发起导航，具体可用的地图 App 由微信与手机系统决定。
- 小程序内无法检测用户安装了哪些地图 App，因此删除原 PRD 中「根据用户已装 App 排序」的交互。
- 小程序内不能使用高德、百度、腾讯地图的 URL Scheme 唤起外部 App；URL Scheme 只用于 V2.0 独立 App。
- 如果业务坚持三地图选择，需要在 V1.1 通过 `wx.navigateToMiniProgram` 分别跳转高德、百度、腾讯小程序，并逐家确认 AppId、路径与参数支持情况。

### 5.3 参数与坐标系


| 参数        | 说明          | 示例             |
| --------- | ----------- | -------------- |
| latitude  | 目标纬度，GCJ-02 | 22.517600      |
| longitude | 目标经度，GCJ-02 | 113.952300     |
| name      | 目的地名称       | 深圳湾公园北湾钓点      |
| address   | 目的地地址       | 南山区滨海大道深圳湾公园北湾 |
| scale     | 地图缩放级别      | 16             |


坐标约定：

- 所有钓点、POI、导航目标统一存储 GCJ-02。
- 腾讯地图、高德地图、微信地图均使用 GCJ-02，无需转换。
- 仅在跳转百度地图小程序或百度地图 App 时，由跳转层做 GCJ-02 到 BD-09 的转换。
- 第三方 POI 数据入库前校验坐标系，避免混入 WGS-84。

### 5.4 降级策略


| 场景                     | 处理                       |
| ---------------------- | ------------------------ |
| 用户拒绝定位                 | 使用深圳默认中心，列表不展示距离，按区域筛选   |

## 6. 数据来源与更新机制

### 6.1 数据来源


| 数据类型     | 主要来源            | 采集方式      | 可信度     |
| -------- | --------------- | --------- | ------- |
| 钓点基础信息   | 水务、海洋、公园等官方公开信息 | 人工录入与定期核查 | 高       |
| 鱼种、收费、钓法 | 钓鱼社区、钓友上报、线下实勘  | 人工审核与用户补全 | 中       |
| 周边场所 POI | 腾讯位置服务或高德开放平台   | API 同步    | 高       |
| 实时情报     | 用户 UGC          | 用户提交与审核   | 低，需时效标签 |


### 6.2 POI 数据方案

默认方案：腾讯位置服务。理由是与微信地图组件、`wx.openLocation` 同属腾讯生态，坐标系与授权链路一致，集成成本低。高德作为备选，需评估 POI 质量、配额与费用。

同步规则：

- 以每个已发布钓点为中心，半径 3 公里。
- 只同步餐饮、停车、厕所、补给、娱乐、住宿六类。
- 每个钓点每类最多保留 50 个 POI，按距离取近。
- 使用 `external_poi_id` 去重；同一 POI 可关联多个钓点。
- 已关闭或异常的 POI 标记为隐藏，不删除历史记录。
- 每日 03:00 增量同步；核心钓点（`is_core=true`）每周做一次全量校验。
- 查询缓存 24 小时；缓存失效时回源，回源失败使用旧缓存。
- 配额使用达到 80% 时告警，达到 95% 时停止非核心钓点同步。
- 周边列表与详情展示数据来源署名。

数据条款与字段约束：

- 上线前确认供应商条款允许 POI 落库、缓存与展示；若不允许，改为实时查询加短缓存，不落库。
- 评分与营业时间为可选字段，接口不返回时 UI 留空，不做占位或推算。
- 署名方式、缓存时长与删除机制按供应商要求执行，必要时写入配置项。

成本控制：

- 优先使用免费配额。
- 限制半径与类型，避免全城拉取。
- 对核心钓点做人工质量校验，其余依赖自动同步。
- 每月统计调用量与费用，超过预算时切换到高德或降低同步频率。

### 6.3 更新机制与信息时效


| 机制     | 说明                           | 频率                  |
| ------ | ---------------------------- | ------------------- |
| 人工核实   | 运营核对开放状态、收费、钓法、图片            | 核心钓点 30 天，其他钓点 90 天 |
| 用户上报   | 用户提交情报，审核通过后进入待核实队列，由运营确认后更新 | 实时，V1.1             |
| POI 同步 | 周边场所数据同步                     | 每日                  |
| 时效提示   | 根据 `verified_at` 展示提示        | 实时计算                |


`verified_at` 更新规则：

- 仅后台「标记已核实」动作更新，普通编辑不更新。
- 导入时的首次核实时间视为一次核实；POI 同步与用户上报通过都不自动更新。
- 每次核实写入操作日志，记录核实人、时间与核实方式。
- 核心钓点名单由运营在后台维护，可随时调整，次日生效。

时效展示规则：

- 核心钓点超过 30 天、其他钓点超过 90 天，展示黄色提示。
- 超过 180 天，展示更强的「信息可能已过期」提示，并降低推荐排序权重；`sort=distance` 时仍按距离排序。
- 禁钓与收费状态变化属于高时效信息，运营发现变化时应立即修改并通过「标记已核实」更新 `verified_at`。
- 后台看板展示过期钓点清单，运营按周清理。

### 6.4 UGC 审核工作流（V1.1）

- 机器审核：文本走 `security.msgSecCheck`，图片走 `mediaCheckAsync`。
- 先发后审：机器审核通过后即展示，进入人工抽查队列。
- 人工抽查：运营在后台通过、驳回或下架，24 小时内完成。
- 举报兜底：用户举报后进入二次审核，24 小时内处理。
- 审核状态机见 3.6。
- 审核人力：V1.1 配置 1 名兼职审核，按每日 50 条预估。
- 违规处理：首次驳回并通知，重复违规限制发言，严重违规封禁账号。

### 6.5 禁钓点收录政策

禁钓点涉及合规风险，采用以下策略：

- 默认不在列表与地图展示禁钓点。
- 筛选面板与搜索页提供「包含禁钓点」开关，默认关闭。
- 开启后，禁钓点在列表与详情页展示红色禁钓标识。
- 禁钓点详情页隐藏导航按钮，只展示位置、禁钓说明与复制地址。
- 禁钓状态必须来自官方公示或运营实勘，记录来源与核实时间。
- 不在任何文案中提供禁钓水域的钓法建议或饵料建议。
- 用户上报的禁钓信息需人工核实后才能更新。

### 6.6 信息可信度与免责

- 钓点开放、禁钓、收费状态属于高时效信息，详情页显著展示核实时间。
- 产品在用户协议中声明：钓点信息仅供参考，最终以现场管理方公示为准。
- 产品不对因信息偏差导致的损失承担责任。
- 产品不鼓励在禁钓区域垂钓，不提供违规垂钓诱导。
- 用户发布内容需遵守法律法规与社区规范，违规内容下架。

## 8. 运营后台（M0）

### 8.1 角色与权限

| 标记已核实         | 是     | 是   | 否   |
| Excel 批量导入    | 是     | 是   | 否   |
| POI 绑定与维护     | 是     | 是   | 否   |

| 后台账号管理        | 是     | 否   | 否   |
| 操作日志查看        | 是     | 仅本人 | 否   |

权限必须服务端校验，不能只靠前端隐藏入口。

V1.0 账号通过种子脚本创建，后台账号管理界面为非 P0；配置项通过种子数据与命令行维护，配置界面为非 P0。

### 8.2 登录与安全

- 账号密码登录，密码使用 Argon2id 或 bcrypt 哈希，最少 12 位。
- 连续 5 次失败锁定 15 分钟，失败提示不区分账号是否存在。
- 登录成功后签发访问令牌（30 分钟）与刷新令牌（8 小时），均通过 HttpOnly、Secure、SameSite Cookie 下发，响应体不返回访问令牌与刷新令牌。
- 写操作校验 CSRF Token 与 Origin；刷新令牌轮换，登出、改密、停用账号后递增 `token_version` 使旧会话失效。
- 超级管理员可重置密码、停用账号；密码重置使用一次性令牌，30 分钟内有效。
- 所有写操作记录操作日志，敏感字段脱敏。
- 超级管理员上线前启用 TOTP；普通管理员 V1.1 可增加微信扫码登录或双因素认证。

### 8.3 钓点管理

- 列表：按状态、区域、名称、更新时间筛选，分页展示。
- 新增与编辑：基础信息、地图选点、图片、周边、发布状态。
- 地图选点：腾讯地图 JS SDK，点击或拖动标记设置钓点坐标与导航坐标。
- 地址：支持关键词搜索与逆地理编码，允许手动修改；导入或批量编辑时可按地址批量地理编码，结果需人工确认。
- 图片：单钓点多图上传、排序、设为封面、删除；上传后自动压缩。ZIP 批量图片导入为 P1。
- 校验：必填字段、坐标范围、字典值、重复钓点告警。
- 发布：发布前校验必填字段与 `verified_at`；发布后小程序可见。
- 标记已核实：运营点击后更新 `verified_at`，可填写核实方式与备注；普通编辑不更新，操作写入日志。
- 下线：下线后小程序不可见，历史数据保留。
- 预览：以小程序卡片样式预览钓点详情。

### 8.4 POI 管理

P0 范围为绑定、解绑、隐藏与同步状态查看；人工校正与批量维护为 P1。

- 按钓点查看已绑定 POI，按类型分组，按距离排序。
- 手动新增 POI：名称、类型、坐标、地址、营业时间。
- 绑定与解绑：从 POI 库选择或新建。
- 隐藏：异常或关闭的 POI 标记为隐藏，不删除。
- 同步状态：展示最近同步时间、成功数量、失败原因。
- 人工校正：运营可修改 POI 类型与名称，修改记录写入日志。

### 8.5 导入与导出

- 下载 Excel 模板，模板列与 3.11 一致。
- 上传后先校验再入库，不直接发布。
- 校验项：必填、字典值、坐标范围、图片文件名、重复钓点。
- 地址地理编码：导入时可按地址批量转 GCJ-02 坐标，结果需运营确认。
- 错误报告：生成 CSV，包含行号、字段、错误原因。
- 导入结果：总行数、成功数、失败数、任务状态。
- 导出：P1，按筛选条件导出钓点与 POI，用于线下核对。
- 批量图片：P1，ZIP 包按钓点编号命名，系统匹配后生成预览，不自动替换封面。
- 单次导入上限 200 行。

### 8.6 审核队列（V1.1）

- 队列：待人工抽查、被举报、已驳回、已下架。
- 操作：通过、驳回、下架、封禁用户。
- 驳回必须填写原因。
- 处理时限 24 小时，超时高亮。
- 所有操作记录审核人与时间。

### 8.7 字典与配置

字典管理为 P0；配置界面为 P1，V1.0 通过种子数据与命令行维护。

- 字典：区域、鱼种、水域类型、场所类型、钓法、POI 类型。
- 配置：地图默认中心与缩放、POI 同步半径、时效阈值、功能开关。
- 字典修改需超级管理员权限。
- 修改后小程序下次请求生效，缓存时间不超过 10 分钟。

### 8.8 操作日志

- 记录：操作人、角色、时间、IP、动作、对象类型、对象 ID、变更前后 JSON。
- 查询：按操作人、动作、时间范围、对象筛选。
- 保留：至少 1 年。
- 导出：支持 CSV。

### 8.9 数据看板

数据看板为 P1，V1.0 末或 V1.1 交付；V1.0 运营可通过钓点列表的状态与核实时间筛选查看临期与过期数据。

- 钓点总数、已发布、草稿、已下线。
- 必填字段完整率。
- 临期与过期钓点数量。
- 有图钓点比例、有 POI 钓点比例。
- 最近导入任务状态。
- POI 同步状态与配额使用。
- V1.1 增加 UGC 待审数量与举报数量。

### 8.10 后台非功能要求

- 后台为纯前端应用，所有数据经 API 读写，不持有数据库凭据，不直连数据库。
- 桌面 Web，适配 1280 像素及以上宽度。
- 支持 Chrome、Edge 最新两个大版本。
- 页面首屏不超过 2 秒，表格分页 20、50、100。
- 图片上传单张不超过 10 MB，服务端压缩。
- 操作需二次确认：发布、下线、删除、批量导入。
- 所有接口服务端鉴权与参数校验。
- 管理端登录凭证使用 HttpOnly、Secure、SameSite 的 Cookie；写操作校验 CSRF Token。
- 配置 CSP、X-Frame-Options、Referrer-Policy，禁止内联脚本。
- 后台域名与 API 域名可分离，必须 HTTPS；CORS 只允许后台域名。

容量基线：

- 100 个已发布钓点、5,000 个 POI、1,000 日活、50 QPS 峰值。
- 单实例 API 在 2 核 4G 下支撑 50 QPS；CPU 持续超过 60% 时扩容。

性能不达标时，优先优化图片、接口字段裁剪、分页与缓存，不牺牲主链路功能。

### 9.2 可用性与容量

- 月度可用性目标 99.9%，按核心公开接口计算；管理后台目标 99.5%。
- 计划维护窗口为 00:00 至 06:00，提前 24 小时通知；数据库迁移优先使用不停机变更。
- API 无状态，可水平扩容；单台服务器故障时，5 分钟内切换或重建。
- 第三方地图或 POI 服务不可用时，主链路降级为列表与复制地址。
- 容量保持 50% 余量，CPU、内存、数据库连接、磁盘任一指标持续超过 70% 时告警。
- 每月统计可用性、错误率与慢请求，低于目标时进入整改。

### 9.3 安全

安全基线按 OWASP ASVS 4.0 Level 2 设计，上线前完成安全评审、依赖扫描、容器扫描与渗透测试。详细控制项见 10.11 与附录 E。

身份与访问：

- 管理端与 C 端使用不同认证域：管理端 HttpOnly、Secure、SameSite Cookie；C 端 Bearer Token。
- 管理端权限使用 RBAC，服务端逐接口校验，越权返回 403；权限变更写入审计日志。
- 密码使用 Argon2id 或 bcrypt 哈希，最少 12 位；连续 5 次失败锁定 15 分钟。
- 超级管理员在 V1.0 上线前启用 TOTP 双因素认证；其他角色 V1.1 视情况推广。
- C 端 Token 短期有效，刷新 Token 轮换；注销、封禁后立即失效。

传输与接口：

- 全站 HTTPS，TLS 1.2 及以上，开启 HSTS；证书自动续期并监控到期时间。
- 公开接口限流：每 IP 每分钟 60 次；写接口每用户每分钟 10 次；登录每 IP 每分钟 5 次。
- 普通 JSON 请求体上限 2 MB，单张图片上限 10 MB，导入文件上限 20 MB；分页 `page_size` 公开接口最大 50，管理端最大 100。
- 参数校验使用 class-validator 或 Zod，启用白名单；数据库访问使用 Prisma 参数化查询。
- 统一错误结构，不返回堆栈、SQL、内部路径或密钥。
- 管理端写操作校验 CSRF Token；CORS 只允许后台域名。iOS 客户端不受浏览器 CORS 约束，通过 Bearer Token 调用公开接口。
- 写接口支持 `Idempotency-Key`，避免重复发布、重复导入。

数据与文件：

- 数据库磁盘加密，备份加密；手机号等 PII 使用 AES-GCM 加密，查询用 HMAC 索引。
- 日志脱敏：不记录密码、Token、手机号、用户坐标、完整地址。
- 图片校验文件头与真实类型，重新编码并去除 EXIF；禁止 SVG 与可执行文件。
- 图片存储使用私有桶加短时签名 URL；CDN 回源鉴权；上传与访问分离。
- 密钥放云密钥管理或环境变量，不进入代码仓库、镜像层、小程序包；每季度轮换。

基础设施与供应链：

- 数据库不开放公网端口，只允许 API 与 Worker 安全组访问；运维通过堡垒机或云厂商会话管理器。
- 容器以非 root 运行，镜像最小化，固定基础镜像版本。
- WAF 开启常见 Web 攻击防护与 CC 防护；安全组最小开放。
- 依赖锁定版本，启用依赖漏洞扫描、SAST、容器镜像扫描；高危漏洞 7 天内修复。
- 每月执行依赖更新与安全补丁；每季度复核权限与密钥。

审计与响应：

- 记录登录、登出、权限变更、导入、发布、下线、导出、删除、配置修改。
- 审计日志至少保留 1 年，只追加不修改；导出审计日志需超级管理员权限。
- 建立安全事件分级与响应流程，P0 事件 15 分钟内响应，24 小时内出具初步报告。

### 9.4 隐私与合规

## 10. 技术实现基线

### 10.1 架构总览

架构原则：前后端分离、模块化单体、多端共用契约、云厂商可迁移。V1.0 不引入微服务与 Kubernetes，避免小团队承担不必要的运维复杂度。

```text
微信小程序 ─┐
iOS App ───┼── HTTPS /api/v1 ──→ Nginx / WAF ──→ API 服务（NestJS）
运营后台 ──┘                                      ├── PostgreSQL 15
                                                  ├── Redis（限流与缓存，可选）
                                                  ├── 对象存储（COS / OBS / OSS）
                                                  ├── 腾讯位置服务
                                                  ├── 微信内容安全（V1.1）
                                                  └── Worker（POI 同步、导入、备份）
```

- 三个客户端只依赖 API，不直连数据库，不持有数据库凭据。
- 运营后台是独立前端，独立域名、独立发布，通过 Cookie 会话访问管理接口。
- 小程序与未来 iOS 使用 Bearer Token 访问公开接口，不共享管理端会话。
- API 无状态，可水平扩容；文件、会话、任务状态不落本地磁盘。
- Worker 与 API 使用同一镜像、不同启动命令，共享领域模块；V1.0 用 Docker Compose 管理。
- 第三方依赖通过适配层封装，替换云厂商或 POI 供应商时不改领域代码。

分离带来的收益与代价：


| 收益                   | 代价                | 应对                            |
| -------------------- | ----------------- | ----------------------------- |
| 小程序、后台、iOS 共用一套领域与接口 | 多一个服务要部署与监控       | Docker Compose、统一日志与告警        |
| API 与后台可独立发布、独立扩容    | 契约变更需要协调多端        | OpenAPI 契约先行、CI 差异检查、版本兼容     |
| 后台不持有数据库凭据，攻击面更小     | 管理端认证与 CSRF 需单独设计 | Cookie 会话、RBAC、CORS 与 CSRF 测试 |
| 后续可替换云厂商或拆模块         | 初期代码量略高于单体后台      | monorepo、共享类型、模块化单体           |


请求链路：

```text
客户端
-> DNS / CDN（静态资源）
-> WAF
-> Nginx（TLS、限流、请求头、静态资源）
-> API（鉴权、参数校验、业务逻辑）
-> PostgreSQL / Redis / 对象存储 / 腾讯位置服务
-> 结构化日志、指标、追踪
```

### 10.2 技术选型


| 层       | 选型                           | 说明                                                      |
| ------- | ---------------------------- | ------------------------------------------------------- |
| 微信小程序   | 原生小程序 + TypeScript           | 不引入 Taro、uni-app；包体小，地图能力直接可用                           |
| iOS App | Swift + SwiftUI，iOS 15 及以上   | V2.0；通过 HTTPS 调用同一 API                                  |
| API 服务  | NestJS + TypeScript          | 模块、Guard、Interceptor、OpenAPI 支持完整；团队 TypeScript 背景可直接上手 |
| ORM     | Prisma                       | 迁移、类型安全、参数化查询；禁止无参数裸 SQL                                |
| 数据库     | PostgreSQL 15 及以上            | 标准 SQL、JSONB、事务、时间点恢复；三家云均有托管版                          |
| 缓存与限流   | Redis，可选                     | 多实例限流、热点字典缓存、任务锁；V1.0 单实例可先不引入                          |
| 运营后台    | Next.js + React + Ant Design | 纯前端；表格、表单、上传组件成熟                                        |
| 地图与 POI | 腾讯位置服务 + 微信 `<map>`          | 与微信生态一致；高德作为备选                                          |
| 对象存储    | COS + CDN，S3 兼容适配层           | 图片上传、压缩、签名访问；可替换 OBS 或 OSS                              |
| 部署      | Docker Compose + Nginx       | 单台云服务器可支撑 V1.0；后续可平滑迁容器服务                               |
| CI/CD   | GitHub Actions               | lint、typecheck、单测、集成测试、镜像扫描、部署                          |
| 可观测性    | Sentry + OpenTelemetry + 云监控 | 错误、指标、追踪统一关联 `request_id`                               |
| 接口文档    | OpenAPI 3.0.3 + Redoc        | 契约即文档；工具链支持 3.1 时再升级；CI 检查破坏性变更                         |
| 分析      | 微信自定义分析 + 服务端事件              | 客户端事件与服务端结果事件对齐                                         |


选型说明：

- API 使用 NestJS 而不是继续用 Next.js API Routes，是为了让小程序、后台、iOS 共享一个长期稳定的服务端契约，避免后台 UI 与服务端生命周期耦合。
- 不选微信云开发作为主架构：云开发适合纯小程序快速上线，但数据库与云函数绑定微信生态，运营后台和 iOS 复用困难，迁移与安全边界也受限。云开发可作为临时原型，不作为生产基线。
- 如果团队是 Java 背景，API 可替换为 Spring Boot，领域模型、数据库与 OpenAPI 契约不变；不建议为了技术新鲜度更换语言。
- 不引入 GraphQL。当前查询模式简单，REST 加固定字段更易缓存、限流与排障。
- 不引入微服务、服务网格、Kubernetes。V1.0 的团队规模与流量不需要，模块化单体更容易保证一致性。
- CI/CD 默认 GitHub Actions；国内网络不稳定时改用腾讯 CODING 或自建 GitLab Runner，流水线阶段不变。
- Sentry 可用 SaaS 或自建；国内访问不稳定时以云监控 APM 为主、Sentry 为辅，错误仍通过 `request_id` 关联。

```text
      dictionaries/    字典与配置

      imports/         Excel 导入与任务
      admin/           后台账号、权限、审计
      analytics/       事件接收与指标
      jobs/            定时任务与任务锁
      health/          健康检查
  admin/               Next.js 运营后台
  miniprogram/         微信原生小程序
packages/
  shared/              类型、枚举、错误码、校验规则
  api-client/          由 OpenAPI 生成的客户端
infra/
  docker/              Dockerfile 与 Compose
  nginx/               反向代理与安全头
```

模块规则：

- Controller 只做参数解析、鉴权与响应封装；业务规则放 Service；数据库访问通过 Prisma Repository。
- 领域模块之间通过 Service 接口调用，不直接读写对方表；禁止跨模块 JOIN 作为默认做法。
- `shared` 只放类型、枚举、错误码、纯函数，不放数据库访问与业务状态。
- 禁止循环依赖；CI 增加依赖图检查。
- 每个模块对外暴露 `index.ts`，只导出允许调用的接口。
- 新增客户端只调用公开 API，不新增服务端分支；客户端差异用 `client_type` 与配置开关表达。
- 定时任务与 API 共享领域 Service，不复制业务逻辑。
- 所有写操作带 `request_id` 与操作者标识，便于审计与排障。

### 10.4 API 约定

基础约定：

- Base path：`/api/v1`；管理端为 `/api/v1/admin`，C 端为 `/api/v1`。
- 编码：UTF-8，`Content-Type: application/json`。
- 字段命名：snake_case；枚举值使用稳定代码：区域用中文标准名称，其余用小写英文；展示文案由客户端字典映射。
- 统一响应结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "req_01H..."
}
```

- 分页响应：`items`、`page`、`page_size`、`total`、`has_more`。
- 错误响应不返回堆栈、SQL、内部路径；`request_id` 用于服务端定位。
- HTTP 状态码表达类别，业务码表达细节；客户端优先看 HTTP 状态，再读 `code`。
- 文件下载类接口成功时返回二进制流与 `Content-Disposition`，不使用 JSON 信封；失败时仍返回统一 JSON 错误。

请求头：


| 请求头                | 必填    | 说明                          |
| ------------------ | ----- | --------------------------- |
| `X-Request-Id`     | 否     | 客户端可传；未传由服务端生成，响应回传         |
| `X-Client-Type`    | 是     | `miniprogram`、`ios`、`admin` |
| `X-Client-Version` | 是     | 客户端版本，例如 `1.0.0`            |
| `Idempotency-Key`  | 写接口按需 | 导入、发布、下线、支付类操作              |
| `Authorization`    | C 端按需 | `Bearer <access_token>`     |


`X-Request-Id` 只接受字母、数字、下划线、连字符，最长 64 字符；非法值由服务端重新生成，避免日志注入。`X-Client-Type` 与 `X-Client-Version` 可伪造，只用于统计与兼容判断，不参与鉴权。

响应头：

- `X-Request-Id`：全链路追踪标识。
- `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`：限流提示。
- `ETag`：字典、配置等可缓存资源。
- `Cache-Control`：公开只读接口按资源设置，默认 `no-store`。
- `Retry-After`：429 响应返回建议重试秒数，客户端做退避，不立即重试。

业务码：


| 业务码   | HTTP | 含义                |
| ----- | ---- | ----------------- |
| 0     | 200  | 成功                |
| 40001 | 400  | 参数错误              |
| 40101 | 401  | 未登录或 Token 无效     |
| 40102 | 401  | Token 过期，需要刷新     |
| 40301 | 403  | 无权限               |
| 40401 | 404  | 资源不存在             |
| 40901 | 409  | 状态冲突，例如重复发布       |
| 40902 | 409  | 幂等键冲突或请求体不一致      |
| 41301 | 413  | 请求体或文件过大          |
| 42201 | 422  | 业务校验失败            |
| 42901 | 429  | 触发限流              |
| 50001 | 500  | 服务内部错误            |
| 50301 | 503  | 依赖服务不可用，例如地图或 POI |


分页与排序：

- `page` 从 1 开始，`page_size` 默认 20；公开接口最大 50，管理端最大 100。
- 排序参数只允许白名单字段；禁止客户端传 SQL 片段。
- 深分页超过 1,000 条时，改用游标分页 `cursor`，V1.1 按需启用。

时间与坐标：

- 时间使用 ISO 8601，服务端存 UTC，响应带 `+08:00` 或统一由客户端格式化。
- 坐标统一 GCJ-02；百度相关跳转在客户端或适配层转 BD-09。
- 金额使用 decimal 字符串，不使用浮点数。

幂等：

- 客户端为同一业务操作生成 `Idempotency-Key`，服务端保存 24 小时。
- 相同 key、相同请求体返回首次结果；相同 key、不同请求体返回 40902。
- 导入任务以文件哈希加操作人作为辅助幂等键。

缓存：

- 字典与配置返回 `ETag`，客户端缓存 10 分钟。
- 钓点列表默认不缓存；详情可缓存 60 秒，发布与下线时主动失效。
- 图片走 CDN，使用内容哈希或随机路径，长缓存。

版本与契约：

- OpenAPI 文件是接口契约的唯一来源，代码与文档同时评审。
- 同一大版本只加字段不删字段；字段废弃先标记 `deprecated`，至少保留 6 个月。
- 破坏性变更升 `/api/v2`，旧版本并行运行至少 6 个月。
- CI 检查 OpenAPI 差异，删除字段、修改类型、收紧必填视为破坏性变更。

数据库约定：

- 主键统一 26 位 ULID 字符串，避免自增 ID 暴露数据量，便于分库与离线合并。
- 时间字段统一 `timestamptz`，服务端写 UTC；展示由客户端或接口层转换。
- 枚举使用 `varchar(32)` 加应用层枚举与数据库 check，不使用 PostgreSQL 原生 enum，降低迁移成本；Prisma schema 用 String 映射，TypeScript 用联合类型或常量校验。
- 金额、坐标、评分使用 `decimal`；禁止浮点数。
- JSONB 只用于扩展元数据，不用于核心筛选字段。
- 软删除表带 `deleted_at`，查询默认过滤；唯一约束需考虑软删除，使用部分索引。
- 外键默认 `ON DELETE RESTRICT`，删除先走业务状态机；不级联删除审计与内容。
- 每个外键、每个列表筛选加排序字段都应有索引；上线前用 `EXPLAIN ANALYZE` 验证前 10 条慢查询。
- 距离排序先用经纬度边界框过滤，再用 Haversine 表达式计算；数据量超过 5,000 时引入 PostGIS 与空间索引。
- 迁移采用 expand-contract：先加字段与双写，再切读，最后删旧字段；禁止在同一次发布中做破坏性变更。
- 迁移前备份，迁移脚本与回滚脚本同时评审；生产迁移在低峰期执行。
- 数据量预估：V1.0 钓点 100 至 500，POI 约 5,000（规划上限 20,000），用户 10,000，内容 50,000；单库足够。

### 10.8 客户端能力与配置

微信小程序：

- `app.json` 增加 `requiredPrivateInfos: ["getLocation"]`。
- `permission.scope.userLocation.desc` 写明「用于计算钓点距离与排序」。
- 首次调用定位前完成隐私授权流程，具体 API 以微信官方文档为准。
- 地图页使用 `<map>` 组件，设置 `latitude`、`longitude`、`scale`、`markers`。
- 聚合使用 `MapContext.initMarkerCluster`，基础库 2.30.0 及以上。
- 导航使用 `wx.openLocation`，传入 GCJ-02 坐标。
- 复制地址使用 `wx.setClipboardData`。
- V1.1 登录使用 `wx.login` 换取 code，后端调用微信接口换取 openid。
- V1.1 内容安全使用 `security.msgSecCheck` 与 `mediaCheckAsync`。
- 小程序实时日志使用 `wx.getRealtimeLogManager`。
- 请求统一走 `packages/api-client`，自动带 `X-Client-Type`、`X-Client-Version`、`X-Request-Id`。
- Token 存小程序本地存储，刷新失败时清理并回到匿名态。

iOS App（V2.0）：

- Swift + SwiftUI，最低 iOS 15；网络层复用 OpenAPI 生成的客户端或轻量封装。
- Token 存 Keychain，不存 UserDefaults；刷新 Token 轮换，注销时清除。
- 登录方式：Sign in with Apple 必须提供；手机号登录可选；微信登录可选。
- 账号注销必须在 App 内可完成，不能只给客服邮箱。
- 推送使用 APNs，设备 Token 写入 `user_device`；推送权限在解释价值后再请求。
- 分享与深链使用 Universal Links；落地页与小程序路径统一由服务端下发。
- 地图导航可唤起高德、百度、腾讯地图 App；百度坐标转 BD-09，Apple 地图按系统实际坐标系验证。
- `Info.plist` 准备定位、相册、通知权限文案；只申请使用期间定位，不申请后台定位。
- 国内上架前完成 App 备案、隐私清单、权限说明与隐私政策；涉及 UGC 时复用同一内容审核接口。
- 不引入第三方广告 SDK；如后续引入，先做隐私与安全评审。

| staging    | 联调、验收、预发布 | 独立数据库，脱敏数据             | 内网或白名单    |
| production | 正式环境      | 托管 PostgreSQL，每日备份     | 公网，WAF 防护 |


域名与入口：

- `api.example.com`：API 服务，HTTPS，小程序合法域名。
- `admin.example.com`：运营后台，HTTPS，仅允许公司网络或白名单访问。
- `/api/v1/admin/*` 与后台页面同样受 IP 白名单或 WAF 访问控制；不能只隐藏后台域名而暴露管理 API。CORS 只约束浏览器，不替代网络层访问控制。
- `static.example.com` 或 CDN：图片与静态资源。
- `staging-api.example.com`：预发布 API，不加入小程序正式域名。

CI/CD 流程：

1. 安装依赖，使用锁文件与缓存。
2. lint、typecheck、单元测试、集成测试。
3. OpenAPI 契约检查，发现破坏性变更直接失败。
4. 构建 API 与后台镜像，执行镜像漏洞扫描。
5. 部署 staging，执行数据库迁移与冒烟测试。
6. 人工审批后部署 production，使用滚动或蓝绿发布。
7. 发布后 10 分钟观察错误率、P95、5xx、数据库连接。
8. 失败时回滚上一版本镜像；数据库迁移保持向后兼容。

部署规则：

- 发布前备份数据库；迁移脚本先在 staging 跑通。
- API 健康检查 `/health` 与 `/ready` 通过后才接入流量。
- 生产至少保留上一版本镜像与配置，回滚时间目标 10 分钟。
- 静态资源带内容哈希，长缓存；HTML 不缓存。
- Nginx 开启 TLS 1.2 及以上、HSTS、gzip 或 brotli、超时与真实 IP；`client_max_body_size` 按接口设置，普通请求 2 MB、图片 10 MB、导入 20 MB。
- 数据库只允许 API 与 Worker 安全组访问，不开放公网。
- 定时任务：每日 03:00 POI 增量同步，每周日 03:30 核心 POI 全量校验，每日 04:00 备份校验。
- Worker 使用数据库 advisory lock 或 Redis 锁，避免多实例重复执行。
- 配置变更走发布流程，紧急变更需双人确认并记录审计日志。

### 10.10 可观测性与运维

日志：

- 结构化 JSON，字段包括 `timestamp`、`level`、`request_id`、`client_type`、`route`、`method`、`status`、`latency_ms`、`error_code`。
- 不记录密码、Token、Cookie、手机号、用户坐标、完整地址。
- Nginx 访问日志关闭 query string 记录，或对 `latitude`、`longitude`、`keyword` 做掩码；API 日志只保留区域级位置。
- 应用日志与访问日志分开；访问日志保留 90 天，应用错误聚合保留 30 天。

指标：

- API：QPS、P50/P95/P99、5xx 比例、4xx 比例、限流次数、慢请求。
- 数据库：连接数、CPU、内存、磁盘、慢查询、复制延迟（如启用）。
- 业务：钓点列表请求、详情请求、导航点击、搜索成功率、POI 同步成功率。
- 任务：导入成功失败、POI 配额、备份结果、证书到期天数。
- 客户端：小程序启动耗时、接口失败率、版本分布。

追踪：

- OpenTelemetry 贯穿 Nginx、API、数据库与外部依赖。
- 采样率 10%，错误请求全量；`request_id` 与 trace_id 关联。
- 外部依赖单独 span，便于判断是自身慢还是第三方慢。

告警：


| 级别  | 场景         | 阈值                | 渠道      | 响应    |
| --- | ---------- | ----------------- | ------- | ----- |
| P0  | 核心接口不可用    | 连续 3 分钟 5xx 超过 5% | 电话加企业微信 | 15 分钟 |
| P0  | 数据库不可用     | 连接失败持续 1 分钟       | 电话加企业微信 | 15 分钟 |
| P1  | 接口 P95 超目标 | 连续 10 分钟超过 2 倍    | 企业微信    | 30 分钟 |
| P1  | POI 配额     | 达到 80%            | 企业微信    | 1 小时  |
| P1  | 备份失败       | 任意一次失败            | 企业微信    | 1 小时  |
| P1  | 证书到期       | 少于 14 天           | 企业微信    | 1 天   |
| P2  | 磁盘使用率      | 超过 80%            | 邮件      | 1 天   |


运维手册至少覆盖：

- API 5xx 升高排查：看错误聚合、数据库连接、第三方依赖、最近发布。
- 数据库连接耗尽：查连接池、慢查询、泄漏、扩容。
- POI 配额超限：降频、停非核心同步、切换备选供应商。
- 证书过期：自动续期失败时手动替换并检查 Nginx。
- 备份失败：检查对象存储权限、磁盘空间、任务日志，补跑并验证。
- 安全事件：隔离、取证、修复、通报、复盘。

### 10.11 安全架构

资产与威胁：


| 资产         | 风险         | 控制                         |
| ---------- | ---------- | -------------------------- |
| 后台账号与权限    | 撞库、越权、会话劫持 | 强密码、锁定、Cookie 安全属性、RBAC、审计 |
| 用户身份与手机号   | 泄露、滥用      | 最小收集、加密、脱敏、访问控制            |
| 钓点与 POI 数据 | 爬取、篡改      | 限流、访问控制、审计、备份、写权限隔离        |
| 图片与 UGC    | 恶意文件、违规内容  | 类型校验、重编码、内容安全、人工审核         |
| 密钥与配置      | 泄露         | 密钥管理、环境隔离、轮换、最小权限          |
| 第三方依赖      | 供应链攻击      | 锁版本、扫描、SBOM、最小依赖           |


信任边界：

- 公网客户端不可信，所有输入必须校验。
- 管理端与 C 端认证域分离，Token 不通用。
- API 与数据库之间为内网信任边界，数据库不暴露公网。
- 第三方回调必须验签、校验时间戳与来源 IP。
- 对象存储不直接暴露写权限，上传经 API 或临时签名。

认证与会话：

- 管理端：登录成功后设置 `access_token`（30 分钟）与 `refresh_token`（8 小时）Cookie，均 HttpOnly、Secure、SameSite=Lax；刷新时轮换，登出清除。后台与 API 应部署在同一主域名的不同子域，保证 Cookie 为 same-site；跨主域会迫使 SameSite=None，不推荐。
- C 端：`access_token` 2 小时，`refresh_token` 30 天；Bearer 传递，刷新轮换；`user.token_version` 在封禁或注销后递增，旧令牌立即失效。后台账号同样使用 `admin_user.token_version`。
- 封禁即时生效通过 `token_version` 校验实现：V1.0 每请求查询版本或使用不超过 60 秒的本地缓存；多实例部署后改用 Redis 缓存版本号。
- 管理端写操作使用双提交 CSRF Token；校验 `Origin` 与 `Referer`。
- 密码使用 Argon2id 或 bcrypt，最少 12 位；禁止常见弱密码；超级管理员上线前必须启用 TOTP，其他角色 V1.1 视情况推广。
- 登录失败统一提示「账号或密码错误」，不区分账号不存在与密码错误，避免账号枚举。
- 登录失败 5 次锁定 15 分钟；异常登录记录 IP、UA、时间并告警。
- 密码重置使用一次性令牌，30 分钟内有效，使用后立即失效；重置成功递增 `token_version`。

授权：

- RBAC 权限点：`spot.read`、`spot.write`、`spot.publish`、`import.run`、`poi.write`、`dictionary.write`、`config.write`、`audit.read`、`admin_user.write`、`report.moderate`。
- 角色映射：`super_admin` 全部；`operator` 内容与导入；`reviewer` 仅审核。
- 默认拒绝；新增接口必须显式声明权限点。
- 数据级权限：运营只能操作被分配区域或全部区域，按需启用；V1.0 默认全量，V1.1 可细分。

输入与输出：

- 所有请求使用 DTO 白名单校验，拒绝未知字段。
- 字符串长度、数组长度、分页大小、文件大小均有上限。
- 富文本不开放；UGC 纯文本加图片，展示时转义。
- SQL 全部通过 Prisma 参数化；禁止字符串拼接。
- 响应只返回必要字段，管理端与 C 端使用不同 DTO。

文件上传：

- 允许 JPG、PNG、WebP；校验文件头，不只看扩展名。
- 先按 EXIF Orientation 旋转，再重新编码并去除 EXIF 与元数据；限制最大边长与文件大小。
- 禁止 SVG、HTML、压缩包直接对外访问。
- 文件名使用随机 ID，不使用用户原始文件名。
- 存储桶私有，读取使用短时签名 URL；CDN 回源鉴权，不开放公共读。
- 上传接口限流，按管理员与 IP 双维度。

基础设施：

- WAF 开启 SQL 注入、XSS、命令注入、恶意扫描、CC 防护。
- 安全组只开放 80/443；SSH 仅堡垒机或白名单 IP，使用密钥登录。
- 容器非 root，只读文件系统，最小基础镜像。
- 管理端配置 CSP、X-Frame-Options、Referrer-Policy、Permissions-Policy；禁止内联脚本，使用 nonce 或 hash。
- 数据库使用独立账号，API 账号只有业务表权限，迁移账号单独管理。
- 生产、staging、local 密钥完全隔离；禁止生产数据落到本地。

供应链与安全开发：

- 依赖锁定版本，启用 Dependabot 或 Renovate。
- CI 执行依赖漏洞扫描、SAST、密钥扫描、镜像扫描。
- 高危漏洞 7 天内修复，严重漏洞 24 小时内评估并缓解。
- 上线前执行 DAST 与渗透测试；至少覆盖越权、注入、上传、CSRF、限流绕过。
- 代码评审必须检查鉴权、输入校验、日志脱敏与错误处理。
- 生成 SBOM，保留至少 1 年。

审计与事件响应：

- 审计日志只追加，应用账号无删除权限；保留 1 年。
- 记录登录、登出、失败登录、权限变更、导入、发布、下线、删除、导出、配置修改。
- `before_json` 与 `after_json` 对手机号、Token、密钥等敏感字段脱敏，不保存完整请求体。
- 安全事件分级：P0 数据泄露或服务被控，P1 越权或批量异常，P2 单点异常。
- P0 15 分钟内响应，2 小时内止损，24 小时内初步报告，72 小时内复盘。
- 事件记录、证据保全、通知合规负责人；涉及个人信息泄露时按法律要求报告。

### 10.12 云与数据库选型

默认方案：腾讯云，广州或深圳周边地域。理由是本项目的微信小程序、腾讯位置服务、内容安全、COS 都在腾讯生态内，域名备案、合法域名、日志与账单管理更顺。

生产优先 CVM，Lighthouse 仅用于测试或低流量；需要负载均衡、多可用区与 WAF 时使用 CVM 加 CLB。


| 能力            | 腾讯云                      | 华为云                | 阿里云                |
| ------------- | ------------------------ | ------------------ | ------------------ |
| 计算            | CVM 或 Lighthouse         | ECS                | ECS                |
| 托管 PostgreSQL | TencentDB for PostgreSQL | RDS for PostgreSQL | RDS for PostgreSQL |
| 对象存储          | COS                      | OBS                | OSS                |
| CDN           | 腾讯云 CDN                  | 华为云 CDN            | 阿里云 CDN            |
| WAF           | 腾讯云 WAF                  | 华为云 WAF            | 阿里云 WAF            |
| 负载均衡          | CLB                      | ELB                | SLB                |
| 位置服务          | 腾讯位置服务                   | 需接腾讯或高德            | 高德                 |
| 短信（V2.0）      | 腾讯云短信                    | 华为云短信              | 阿里云短信              |
| 监控            | 云监控 + CLS                | CES + LTS          | CloudMonitor + SLS |


数据库原则：

- 引擎使用标准 PostgreSQL 15，不使用 GaussDB、PolarDB、TDSQL 的专有内核或专有语法。
- 使用托管版，开启自动备份、时间点恢复、监控与告警；不自行编译数据库。
- 生产开启多可用区；V1.0 至少每日备份加 WAL 归档。
- 连接数按实例规格限制，API 连接池小于数据库上限的 70%。
- 迁移使用 `pg_dump` / `pg_restore` 或逻辑复制；对象存储使用跨云同步工具。

可迁移设计：

- 数据库只用标准 SQL 与 Prisma 支持的特性；避免云厂商专有扩展。
- 对象存储通过 S3 兼容接口访问，COS、OBS、OSS 均有兼容层；代码不直接依赖某家 SDK。
- 部署使用 Docker 镜像与环境变量，不依赖云函数、云数据库专有 API。
- 域名、证书、DNS 与云厂商解耦；迁移时先切流量再下线旧资源。
- 单云部署，不做多云双活；用标准协议与备份保留迁移能力。
- ICP 备案与云厂商绑定，选择未来 1 至 2 年不打算搬迁的云。

成本估算见 10.13 节。云厂商报价随地域、规格与活动变化，第 0 周以实际询价为准。

### 10.15 扩展路线

V1.0 保持模块化单体，按触发条件演进，不提前拆分。


| 触发条件                               | 演进动作                             | 说明                     |
| ---------------------------------- | -------------------------------- | ---------------------- |
| API 持续超过 200 QPS 或单实例 CPU 持续超过 60% | API 水平扩容，Nginx 或 CLB 负载均衡        | 无状态服务，优先加实例            |
| 多实例限流或热点缓存                         | 引入 Redis                         | 限流、会话、字典缓存、任务锁         |
| 钓点超过 5,000 或距离查询复杂                 | 引入 PostGIS 与空间索引                 | 先用标准 PostgreSQL 扩展     |
| 搜索 QPS 超过 50 或需要分词排序               | 引入 Meilisearch 或 OpenSearch      | 通过 SearchPort 适配，不侵入领域 |
| 异步任务超过 100 个每天或任务超过 5 分钟           | 引入 BullMQ 或独立队列                  | 保留任务表作为审计              |
| 数据库读 QPS 超过 500 或 CPU 超过 60%       | 增加只读副本，读写分离                      | 报表与列表读走副本              |
| 团队超过 8 人或模块发布互相阻塞                  | 按模块拆服务，优先 auth、media、search、jobs | 先拆边界清晰的模块              |
| 多城市扩展                              | `city_code` 分区、城市字典、城市运营权限       | 数据模型已预留                |
| iOS 上线                             | 新增客户端，复用 `/api/v1` 与 OpenAPI     | 不改领域模型，只加认证方式          |
| 后台权限细化                             | 数据级权限、区域权限、审批流                   | RBAC 权限点已预留            |
| 内容与运营规模扩大                          | 审核工作流、内容质量分、举报处理 SLA             | V1.1 起逐步建设             |


扩展原则：

- 先加索引、缓存、只读副本，再考虑拆服务。
- 拆服务前先稳定模块边界与契约，不做分布式事务。
- 跨服务一致性使用 outbox 或幂等重试，不引入两阶段提交。
- 功能开关与灰度发布优先于长期分支。
- 每次架构变更记录 ADR，写清背景、选项、决定与代价。

V1.0 推荐落地组合：腾讯云 CVM + 托管 PostgreSQL 15 + COS + WAF + CLB；API 用 NestJS + Prisma；后台用 Next.js + React + Ant Design；小程序用原生 TypeScript；部署用 Docker Compose + Nginx；CI 用 GitHub Actions 或腾讯 CODING。该组合能在 9 至 13 周内交付，并保留向华为云、阿里云与 iOS 扩展的路径。

### 12.5 安全测试

鉴权与授权：

- 未登录访问后台接口，返回 401；令牌过期返回 40102；刷新后旧令牌不可再用。
- 运营账号访问超级管理员接口，返回 403；只读账号调用写接口返回 403。
- 越权读取其他钓点草稿，返回 403 或 404；直接改 `spot_id` 不能绕过。
- C 端 Token 访问管理端接口被拒绝；管理端 Cookie 访问 C 端接口被拒绝。
- 注销或封禁后，旧 Token 在 1 分钟内失效。

Web 安全：

- 管理端写接口缺少 CSRF Token 返回 403；`Origin` 不在白名单返回 403。
- CORS 只允许后台域名；预检请求不返回通配符。
- SQL 注入、XSS、模板注入、命令注入测试用例被拦截。
- 上传伪装成 JPG 的 PHP、SVG、HTML、压缩包被拒绝；超大文件返回 413。
- 上传图片的 EXIF 被清除；原始文件名不进入响应或存储路径。
- 错误响应不包含堆栈、SQL、内网地址、依赖版本。

滥用与稳定性：

- 公开接口按 IP 限流，登录接口按账号加 IP 限流，超限返回 429。
- 分页 `page_size` 公开接口超过 50、管理端超过 100 被拒绝或截断；未知字段被拒绝。
- 重复提交相同 `Idempotency-Key` 返回首次结果；不同请求体返回 40902。
- 慢请求与超大请求体触发 Nginx 或 API 限制，不拖垮服务。

基础设施与供应链：

- 数据库端口不对公网开放；安全组只允许 API 访问。
- 容器以非 root 运行；镜像无高危漏洞。
- 依赖漏洞扫描无高危项；密钥扫描无硬编码密钥。
- TLS 配置合格，HSTS、安全响应头生效。
- 备份文件加密，访问备份需要独立权限。

- 小程序与 Mock 客户端请求同一接口，字段缺失、类型不一致视为失败。
- 新增字段不破坏旧客户端；删除字段必须先废弃至少 6 个月。
- 错误码在客户端有统一映射；未知错误码展示通用文案并上报。
- 分页、幂等、限流在三个客户端行为一致；令牌刷新在认证接口就绪后补测。

### 12.7 部署与灾备验收

- staging 与 production 使用同一镜像、同一数据库大版本、同一迁移脚本。
- 生产发布前自动备份；迁移失败可回滚，回滚后旧版本可读。
- 从最近一次全量备份加 WAL 恢复到新实例，核心表行数与校验和一致。
- 模拟 API 实例故障，负载均衡摘除后服务在 30 秒内恢复。
- 模拟数据库主库故障，托管实例自动切换，API 重连后恢复。
- 模拟对象存储不可用，图片降级为占位图，列表与详情不崩溃。
- 发布后 10 分钟内错误率、P95、5xx 在阈值内，否则自动或手动回滚。

### 12.8 用户验收

- 内部 5 人，覆盖产品、开发、运营、测试、设计。
- 外部 3 至 5 名真实钓友，覆盖新手、休闲、资深三类用户。
- 验收场景：周末去哪钓、查看详情并导航、查看周边配套、拒绝定位后继续使用。
- 验收通过标准：主链路无阻断问题，文案可理解，导航可用，数据可信。
- 验收记录与遗留问题清单归档。

### 13.2 审核与发布

- 微信小程序审核通常需要 1 至 7 天，首次提交预留 2 周缓冲。
- 提交前准备：功能截图、类目说明、隐私说明、测试账号（如需要）。
- 审核驳回常见原因：类目不符、隐私说明不完整、定位权限描述不清、内容涉及违规。
- 发布采用分阶段发布：先 10%，观察 24 小时，再全量。
- API 与后台独立发布：先发向后兼容的 API，再发后台；小程序版本不依赖后台发布时间。
- 发布顺序：数据库迁移 -> API -> Worker -> 后台 -> 小程序。任何一步失败先停，不继续后续步骤。
- 回滚方案：保留上一版本代码与镜像；数据库迁移保持向后兼容；出现阻断问题时先回滚 API 或小程序版本，再排查数据库。
- 发布后 7 天为观察期，每日汇总错误率、P95、导航成功率、反馈量；观察期内不做非必要架构变更。
- 安全事件或数据异常时，优先止损与保留证据，再按 10.11 节流程处理。
