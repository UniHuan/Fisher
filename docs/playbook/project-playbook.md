# 从 0 到 1 的项目推进手册

- 基于 SZFisher（深圳钓鱼助手）2026-11-12 至 2026-11-20 的真实推进过程
- 用途：后续新项目启动、排期、验收和复盘时参考
- 配套：`CLAUDE.md` 的做事顺序与工程准则、`docs/superpowers/` 的设计与计划、`docs/adr/` 的架构决策

## 0. 一页结论

一个项目从想法到上线，真正的顺序是：

```text
需求与边界 -> 技术底座 -> 可运行骨架 -> 按 Epic 交付 -> staging
-> 数据质量 -> 合规与客户端 -> 生产基础设施 -> 灰度上线 -> 反馈与下一版
```

最容易犯的错误，是把“功能写完”当成“项目快完成”。SZFisher 的实际情况是：V1.0 功能代码和 staging 已经跑通，但公开上线仍被核心内容、图片、核实、小程序改名与备案、生产基础设施卡住。**代码往往不是最后瓶颈，内容、合规和运维才是。**

## 2. 工作方式

### 2.1 分工

- 用户：产品范围、真实需求、云控制台、密钥、法务、数据核实、预算、上线批准。
- Claude：代码、文档、测试、staging 操作、数据整理、检查清单、自动化、评审。
- 共同：阶段目标、优先级、验收标准、是否上线。

### 2.2 沟通

- 先给结论，再说过程。
- 每次只问会改变方案的问题，其余做合理默认并说明。
- 明确“已完成、未完成、阻塞、下一步”，不要用“应该可以”代替验证。
- 密钥、AppSecret、AccessKey、token 不进入聊天、仓库、日志或截图。

### 2.3 决策与留痕

- 架构级决策写 ADR，例如 `docs/adr/ADR-011-postgresql-18.md`。
- 新功能先设计文档，再实现计划，再写代码。
- 运营和数据操作写清楚环境、范围、回滚方式；直接改生产数据默认禁止。
- 每个 PR 说明动机、改动、验证和风险。

## 3. 阶段推进法

### 阶段一：需求与边界

输入：一个想法、用户痛点、商业目标。

动作：

1. 写一页项目章程：为谁解决什么问题，成功标准是什么。
2. 写 PRD：范围、非目标、角色、流程、数据、指标、风险。
3. 列出所有未知项：数据来源、合规、预算、审核、依赖方。
4. 先做减法：V1.0 只保留能验证核心价值的功能。

输出：PRD、范围清单、非目标清单、成功指标、未知项。

门禁：能一句话说清“谁在什么场景下为什么用”，并且知道 V1.0 不做什么。

SZFisher 的做法：V1.0 只做钓点查询、地图、详情、POI、后台和导入；UGC、个人中心、天气潮汐留到 V1.1。

### 阶段二：技术底座

输入：PRD、团队能力、预算。

动作：

1. 选技术栈，写 ADR，明确不选什么。
2. 搭 monorepo：API、后台、客户端、共享包、openapi、infra、docs。
3. 先跑通一条最小链路：数据库、API、后台、客户端、CI。
4. 从第一天建立测试、lint、typecheck、OpenAPI 契约和审计日志。
5. 建立设计系统或至少配色、字体、间距、组件规则。

输出：可启动的骨架、CI、测试命令、目录规范、ADR。

门禁：干净环境能一条命令启动，CI 能跑 lint、typecheck、test、build。

SZFisher 的做法：NestJS、Prisma、PostgreSQL 18、Next.js 静态后台、原生 TypeScript 小程序、pnpm、OpenAPI 生成客户端类型。

### 阶段三：按 Epic 交付

输入：主计划、Epic 列表。

动作：

1. 把主计划拆成 Epic，再把 Epic 拆成可独立验收的任务。
2. 每个任务先写失败测试，再实现，再跑测试，再审查，再提交。
3. 使用隔离分支或 worktree，避免互相污染。
4. 每个 PR 保持外科手术式修改，只碰必须碰的文件。
5. 每个阶段结束做一次整分支审查，不把问题留到上线。

输出：可运行的功能、测试、PR、更新后的文档。

门禁：任务测试通过、审查通过、CI 通过、没有未解释的 TODO。

SZFisher 的做法：E1 到 E8 分 Epic 推进；后台钓点单独 Epic；每个 Epic 都有计划和测试。

### 阶段四：staging 先行

输入：可运行的功能、云账号、域名。

动作：

1. 先建 staging，不直接上生产。
2. 资源最小化：1 台 ECS、RDS、OSS、DNS、TLS、Nginx、Docker。
3. 密钥只放服务器环境文件，权限 600，不进仓库。
4. 数据库迁移、种子、健康检查、备份、日志轮转一次做齐。
5. 每个外部依赖都做真实验证：OSS 读写、地图 Key、短信、对象复制、TLS。

输出：可访问的 staging、健康检查、部署文档、回滚方式。

门禁：HTTPS 200，API 健康，后台能登录，核心链路可用，备份可恢复。

SZFisher 的教训：Docker Hub 不可达、APT/npm 慢、PG18 数据目录变化、OSS copy 源桶错误、后台 CSP 拦截腾讯地图，这些都在 staging 暴露，而不是生产。

### 阶段五：数据质量

输入：数据源、导入模板、质量门禁。

动作：

1. 先确认数据来源和授权，尤其是图片和第三方字段。
2. 用 Excel 或 API 导入，保留批次、错误行和审计。
3. 建质量报告：总量、必填、禁钓、开放、核心、图片、POI、核实新鲜度。
4. 定义核心集合，不要平均用力；先做 50 个核心点。
5. 先补真实图片和核实，再扩量。
6. POI 等外部额度受限的同步，用夜间小批量，不要一次打满。

输出：质量报告、核心清单、图片计划、核实计划、POI 计划。

门禁：质量门禁通过，或明确记录接受的例外。

SZFisher 的现状：106 条已发布，49 条有 POI，核心 2/50，图片 0，100 条核实过期；质量门 5/8。核心内容和水印图片是公开上线前最重要的工作。

### 阶段六：客户端与合规

输入：客户端代码、AppID、类目、隐私政策。

动作：

1. 用真实 AppID 和真实设备，不用测试号糊弄。
2. 先跑通开发版、体验版，再提交审核。
3. 配合法域名、上传域名、下载域名、业务域名。
4. 隐私指引、用户协议、社区规范先上线。
5. 改名、图标、简介、类目、备案变更提前做，审核有周期。
6. UGC 类目在开发前确认，不要做完才发现不能上。

输出：体验版、审核材料、隐私与协议、发布检查表。

门禁：真机通过、隐私合规、类目与备案明确、审核材料齐全。

SZFisher 的教训：小程序空白页是 TypeScript 编译插件没开；体验版路径是 `pages/index/index`；旧名称“瑞环门球”必须改；UGC 类目还没确认。

### 阶段七：生产基础设施

输入：staging 验收、生产预算、合规。

动作：

1. 生产和 staging 分离，生产至少 2 台 API、RDS 高可用、SLB、WAF、CDN、ACR、监控、备份。
2. 多实例前，先解决共享限流、定时任务锁、会话和缓存。
3. 图片走 CDN 或明确的公开读取路径；私有桶不开公共读。
4. 生产数据只走后台流程，保留逐条审计。
5. 做恢复演练、安全扫描、压测和灰度方案。
6. 明确 go/no-go 条件，不满足就不发。

输出：生产环境、监控、备份、发布方案、回滚方案、go/no-go 记录。

门禁：生产演练通过，监控告警可用，备份可恢复，合规材料齐全。

SZFisher 的现状：生产未开始；CDN、WAF、SLB、ACR、监控、备份、2 台 ECS 仍在计划中。

### 阶段八：上线与迭代

输入：生产环境、审核通过、灰度名单。

动作：

1. 小流量灰度，观察错误率、时延、内容举报、审核积压。
2. 功能开关保护新功能，出问题能立即关闭。
3. 每周看质量、内容、审核、成本和用户反馈。
4. 用真实反馈决定下一版，不凭想象堆功能。
5. 下一版先设计、再计划、再实现，不边做边想。

输出：上线记录、监控数据、反馈清单、下一版设计。

门禁：核心指标稳定，严重问题清零，回滚演练通过。

## 4. 可复用检查清单

### 4.1 立项清单

- [ ] 一句话说清用户、场景、价值。
- [ ] PRD 有范围和非目标。
- [ ] 成功指标可量化。
- [ ] 数据来源和授权明确。
- [ ] 合规、类目、备案、隐私有负责人。
- [ ] 预算和上线时间有初步判断。
- [ ] 未知项列成清单，不藏在心里。

### 4.2 架构清单

- [ ] 技术栈和 ADR。
- [ ] 最小可运行链路。
- [ ] 数据库迁移和种子。
- [ ] 测试、lint、typecheck、CI。
- [ ] OpenAPI 和客户端类型生成。
- [ ] 审计日志和错误码。
- [ ] 密钥管理和环境变量。
- [ ] 备份、日志、监控预留。

### 4.3 任务执行清单

- [ ] 读设计文档和相关代码。
- [ ] 写失败测试。
- [ ] 跑测试确认失败。
- [ ] 最小实现。
- [ ] 跑测试通过。
- [ ] 自查 spec 覆盖、类型、边界。
- [ ] 独立审查。
- [ ] 提交并写清验证。

### 4.4 staging 清单

- [ ] ECS、RDS、OSS、DNS、TLS、Nginx、Docker。
- [ ] 环境文件 600，密钥不在仓库。
- [ ] 数据库迁移和种子。
- [ ] API 健康、后台登录、HTTPS 200。
- [ ] OSS 读写删、地图 Key、第三方额度实测。
- [ ] 日志轮转、备份、恢复演练。
- [ ] 部署文档和回滚步骤。

### 4.5 数据清单

- [ ] 来源和授权。
- [ ] 导入模板和错误报告。
- [ ] 必填完整。
- [ ] 禁钓、开放状态。
- [ ] 核心集合。
- [ ] 图片真实或授权。
- [ ] 核实时间和新鲜度。
- [ ] POI 覆盖和额度。
- [ ] 质量报告和环境记录。

### 4.6 小程序发布清单

- [ ] 真实 AppID 和真实设备。
- [ ] TypeScript 编译插件。
- [ ] 合法域名、上传域名、下载域名、业务域名。
- [ ] 隐私指引、用户协议、社区规范。
- [ ] 名称、图标、简介、类目、备案。
- [ ] 体验版和体验成员。
- [ ] 版本号、页面路径、截图。
- [ ] 审核材料、应急联系方式。

### 4.7 生产清单

- [ ] 2 台以上 API、RDS 高可用。
- [ ] SLB、WAF、CDN、ACR。
- [ ] 监控、告警、日志、备份。
- [ ] 共享限流、定时任务锁。
- [ ] 数据库迁移和回滚。
- [ ] 图片公开路径和缓存。
- [ ] 安全扫描和压测。
- [ ] 灰度、回滚、go/no-go。

### 4.8 安全清单

- [ ] 密钥不入库、不入日志、不入聊天。
- [ ] 私有桶不开公共读。
- [ ] 上传校验文件头、重编码、限大小。
- [ ] 后台 RBAC 和审计。
- [ ] 用户内容机审、人审、举报。
- [ ] 限流和防刷。
- [ ] 依赖审计和升级。
- [ ] 备份加密和恢复演练。

## 6. 常见错误与对策

| 错误 | 后果 | 对策 |
| --- | --- | --- |
| 先写代码后想需求 | 返工 | 先 PRD 和设计，再计划 |
| 功能一次全做 | 迟迟不能上线 | 按 Epic 交付，先核心后扩展 |
| 直接改生产数据库 | 无审计、不可回滚 | 生产只走后台流程，staging 直改也需明确批准 |
| 密钥进聊天或仓库 | 泄露 | 服务器 600 环境文件，聊天只出现变量名 |
| 跳过 staging | 生产踩坑 | staging 先行，真实依赖实测 |
| 没有质量报告 | 内容空、过期 | 质量门禁和核心集合 |
| 图片没有授权 | 法务风险 | 真实或授权图片，记录来源 |
| 小程序类目没确认 | 做完不能上 | 开发前确认类目和 UGC 声明 |
| 多实例只做进程内限流 | 限流失效 | Postgres 共享计数或 WAF |
| 定时任务多实例重复跑 | 重复数据处理 | advisory lock 或单实例 |
| CI 红了还合并 | 质量债 | 先修复或明确记录例外 |
| 依赖审计失败 | 安全风险 | 及时 override 或升级，保留锁文件 |
| 文档只存在聊天里 | 无法交接 | 写入仓库，PR 化 |
| 只报“应该可以” | 无法判断 | 用命令和输出证明 |

## 8. 新项目启动 10 步

1. 写一页项目章程和 PRD。
2. 列非目标、未知项、合规和数据来源。
3. 写架构 ADR，搭最小可运行骨架。
4. 建 CI、测试、OpenAPI、错误码、审计。
5. 拆 Epic 和任务，先做核心链路。
6. staging 先行，真实依赖实测。
7. 建数据质量报告和核心集合。
8. 客户端真机、体验版、隐私和类目。
9. 生产 HA、WAF、CDN、监控、备份、灰度。
10. 用反馈设计下一版，功能开关保护新功能。
