# UniHuan 商城 M7 落地路线

日期：2026-11-21  
状态：已确认，待执行  
关联文档：`docs/PRD_v1.4.md`（v1.5 商城增补稿）、`docs/PRD_v1.4_增补_UniHuan商城M7.md`、`docs/superpowers/specs/2026-11-21-unihuan-commerce-extension-design.md`

## 1. 结论

M7 完整商城不和 V1.1 体验版抢同一个上线窗口。V1.1 先把钓友情报、体验反馈和微店内容卡跑起来，验证内容和用户需求；M7 作为独立里程碑，按「立即购买 MVP、再购物车、再自助售后」的顺序推进。

Phase 1 已经合并的 commerce 模块不推倒，作为 M7 的商品目录、推荐和内容卡底座。

## 2. 已确认的决策

| 决策 | 结论 | 影响 |
| --- | --- | --- |
| M7 版本位置 | 独立商城里程碑，排在 V1.1 体验版之后 | V1.1 体验不被支付、订单和售后阻塞 |
| 第一版购买范围 | 只做立即购买，不做购物车 | 符合 PRD 7A.11 的缩减顺序，开发周期最短 |
| 第一版售后 | 后台人工退款，不做用户自助售后 | 减少用户侧表单和状态机 |
| 第一版 SKU | 保留 SKU 表，但大部分商品单 SKU | 数据结构不返工，页面先简单 |
| 渠道策略 | 保留 `product_channel` 作为微店兜底；原生下单走新的 `native` 模式 | 两条路径共存，不互相绑死 |
| 数据模型 | 趁没有真实商品数据，按 PRD v1.5 对齐一次 | 避免上线后迁移商品和库存 |
| 合规节奏 | 合规和供应链与体验版并行启动 | 支付商户号和电商类目周期最长，必须前置 |

## 3. 两条购买路径

用一个配置区分，不要在一个页面里混两套逻辑：

```text
shop_mode = outbound | native
```

| 模式 | 商品卡点击 | 适用阶段 |
| --- | --- | --- |
| `outbound` | 跳微店小程序、H5 或复制链接 | Phase 1，已在 main，默认关闭 |
| `native` | 进入商品详情，选规格，立即购买，微信支付 | M7 MVP |

`product_channel` 表继续保留，`native` 模式下可以不配置渠道，商品卡直接使用 `product_sku` 的价格和库存。

## 4. 数据模型对齐

Phase 1 和 PRD v1.5 的命名差异需要在 M7 开工前一次处理完，当前没有真实商品数据，成本最低。

| Phase 1 | PRD v1.5 / M7 | 处理 |
| --- | --- | --- |
| `product.title` | `product_name` | 重命名 |
| `product.image_keys` | `images` | 重命名 |
| `status active` | `status on_sale` | 迁移取值 |
| `status archived` | `status off_shelf` | 迁移取值 |
| `product_channel` | 无对应表 | 保留，作为 outbound 渠道 |
| `product_placement` | `product_recommendation` + `product_fish_map` | 保留人工位置，规则推荐新增；两者合并返回 |
| 无价格 | `price`、`market_price`、`cost_price` | 新增 |
| 无 SKU | `product_sku` | 新增 |
| 无库存 | `stock_total`、`sku.stock` | 新增 |
| 无订单 | `order`、`order_item` | 新增 |
| 无售后 | `refund` | 新增 |
| 无购物车 | `cart_item` | 第二阶段再加 |

## 5. 分阶段计划

### 阶段 A：V1.1 体验版，第 1 到 2 周

- 招募 5 到 8 位体验成员，加入体验成员名单
- 第一周验证浏览、登录、发文字、发图片、反馈五条链路
- 每天 10 分钟后台分流，P0 当天、P1 三天、P2 每周汇总
- 微店内容卡保持 `features.shop=false`，拿到微店链接后再开 staging 冒烟
- 输出体验反馈汇总和是否继续投入 M7 的判断

### 阶段 B：合规与商品准备，与阶段 A 并行

- 营业执照主体和经营范围核对
- 微信支付商户号申请，绑定小程序 appid
- 小程序服务类目增加电商相关类目，确认自有品牌销售口径
- 隐私保护指引补充收货地址、手机号、订单信息
- 商品详情富文本和图片接入内容安全
- UniHuan 商标第 28 类注册
- 首批 20 个 SKU 的商品名、价格、库存、图片、详情文案
- 确定深圳本地仓和发货时效

**Gate B**：微信支付商户号可用、电商类目通过、20 个 SKU 数据齐备。未通过不进入阶段 C。

### 阶段 C：M7 MVP，第 3 到 6 周

范围：

- 商品详情页，含 SKU、价格、库存状态、适配钓点/鱼种
- 钓点详情推荐装备区复用 Phase 1 的商品卡
- 立即购买，不做购物车
- 收货地址：优先复用微信地址组件，保留手动输入兜底
- 创建订单、微信支付、支付回调、30 分钟未支付关单
- 库存行级锁扣减，失败回补
- 订单列表、订单详情
- 后台订单列表、发货、备注
- 后台人工退款，微信原路退回

不包含：

- 购物车
- 用户自助售后
- 多 SKU 复杂选择器
- 推荐规则自动化
- 京东等其他渠道
- 积分、优惠券、会员价

**Gate C**：staging 完成支付成功、支付失败、重复回调、超时关单、库存并发、退款六类验收。

### 阶段 D：M7 增强，MVP 稳定后

- 购物车
- 用户自助售后和退货退款
- 多 SKU 选择器
- `product_fish_map` + `product_recommendation` 规则推荐
- 库存预警和数据看板
- 京东等其他渠道
- 优惠券、会员价、积分

## 6. 后台扩展

复用现有 RBAC、审计和登录体系，新增「商城」一级菜单。

| 功能 | 超级管理员 | 运营 | 审核员 |
| --- | --- | --- | --- |
| 商品管理 | 是 | 是 | 否 |
| 库存管理 | 是 | 是 | 否 |
| 订单管理与发货 | 是 | 是 | 否 |
| 售后审核 | 是 | 是 | 是 |
| 推荐规则配置 | 是 | 是 | 否 |

新增权限：`product:read`、`product:write` 已有；新增 `order:read`、`order:ship`、`refund:read`、`refund:handle`、`stock:write`。所有写操作写审计。

## 7. 非功能门禁

- 支付回调验签、金额核对、`transaction_id` 幂等入账
- 库存扣减使用条件更新和事务，不超卖
- 订单状态机条件更新，重复支付、重复取消返回 409
- 地址和手机号加密存储，日志脱敏
- 商品详情和图片过内容安全
- 下单、支付、退款埋点关联 `request_id` 和 `order_no`
- 退款和订单数据保留周期符合财务和法务要求

## 8. PRD 待修

PRD v1.5 已插入 M7，但有几处需要下一版同步修正：

1. 1.1 产品定位仍写「不做电商闭环」，与 1.5、7A 冲突
2. 7.3 的 V1.1 范围列表没有 M7，但 2.3 和 7A 把 M7 放在 V1.1
3. M6 的天气、潮汐在模块表和 7.4 的版本归属不一致；收藏和足迹当前代码未实现
4. M7 写的是 V1.1 完整闭环，本路线把它调整为「V1.1 体验版 + 独立 M7 商城里程碑」，PRD 需要确认这个口径

在本路线执行期间，交付顺序以本文档为准；PRD 负责产品定义，本文档负责落地顺序。

## 9. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 微信支付商户号和电商类目延迟 | M7 无法按期开工 | 阶段 B 立即启动，Gate B 前置 |
| 商品和库存数据不准 | 超卖或退款纠纷 | 首批只上 20 个 SKU，先小规模灰度 |
| 支付回调重复或丢失 | 重复入账或漏单 | 回调和主动查询双确认，幂等键 |
| 地址和手机号合规 | 隐私指引或审核被拒 | 加密存储、日志脱敏、隐私指引提前更新 |
| 购物车和自助售后范围膨胀 | MVP 延期 | 严格按本文档阶段 C 范围执行 |
| M7 与 V1.1 体验抢资源 | 两边都延期 | 体验版先跑，M7 在 Gate B 通过后开工 |
