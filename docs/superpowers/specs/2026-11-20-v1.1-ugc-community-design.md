# SZFisher V1.1 M5 钓友情报设计

- 日期：2026-11-20
- 状态：设计已批准，待实现计划；实现等 V1.0 稳定后开始
- 批准日期：2026-11-20
- 范围：V1.1 M5 用户内容与情报
- 关联文档：`docs/PRD_v1.4.md` 3.5、3.6、3.7、4.2 流程三、6.4、8.1、8.6、10.3、10.5、11.3
- 前置结论：V1.0 先完成内部测试与稳定；本设计现在评审，V1.0 稳定后再排期实现
- 一句话：在每个钓点详情页增加公开的「钓友情报」区，登录用户可发评论、晒鱼获、报现场情报，可点赞和举报；机器审核通过即展示，人工抽查与举报兜底；运营在后台审核并将有价值的情报用于更新钓点。

## 1. 为什么要做

V1.0 的钓点信息由运营录入和核实，能解决「去哪里钓」，但解决不了「现在怎么样」。钓友到现场后发现的收费变化、开放状态、鱼口、停车和厕所情况，目前没有低成本的回传通道。数据会过期，运营也不可能每周跑完 100 多个点。

内部测试收到的建议是：每个钓点给一个开放评论区，用户去了就发评论、拍照片，钓到鱼可以炫耀，大家互相比较，同时帮助完善钓点信息。这个建议同时解决了三件事：

1. 信息新鲜度：现场用户补上运营看不到的实时变化。
2. 信任与趣味：真实照片、鱼获和点赞让钓点页有人的痕迹，不再只是静态资料。
3. 内容冷启动：V1.1 的激活抓手是用户内容，先从一个钓点一个钓点地积累，不做空泛的全局社区。

这也是 PRD V1.1 M5 的范围。V1.0 不提前塞入 UGC，避免在数据质量和审核能力没准备好时引入不可控内容。

## 2. 目标、非目标、反目标

### 2.1 目标

| 编号 | 目标 | 可验证结果 |
| --- | --- | --- |
| G1 | 每个已发布钓点有公开的「钓友情报」区 | 未登录用户可读；详情页有入口和内容 |
| G2 | 登录用户可发三类内容 | 评论、鱼获、情报；正文 1 至 500 字；最多 6 张图；鱼获可填鱼种和重量 |
| G3 | 内容可互动 | 点赞、取消点赞、举报、删除自己的内容 |
| G4 | 内容安全 | 文本与图片都经过机器审核；人工抽查；举报 24 小时内处理；不出现未审核内容 |
| G5 | 运营可闭环 | 后台审核队列、通过、驳回、下架、封禁用户、采纳情报 |
| G6 | 可安全上线 | 功能开关默认关闭；staging 验证后开放；关闭开关可立即隐藏写入口 |
| G7 | 合规 | 微信登录、隐私政策、UGC 条款、内容审核记录、用户删除入口齐全 |

### 2.2 非目标

以下不做，或者明确留给 V1.1 之后：

- 全局内容流、关注、私信、评论楼中楼。PRD 已把这些列为不做。
- 个人主页、收藏、足迹、天气、潮汐。这些属于 M6，M5 只做最小登录。
- 榜单、积分、等级、签到、徽章。鱼获先按时间展示并用点赞数比较，周榜留到 V1.1.x。
- 视频、语音、直播、富文本、@ 提及、外链。正文只接受纯文本。
- 用户直接编辑钓点资料。情报只作为运营更新钓点的依据，不能自动改公开数据。
- 微信订阅消息、推送、站内信。审核结果只在小程序内通过 `GET /auth/me` 一次性提示，不做推送。
- 内容搜索、话题、标签体系。
- 多语言。

### 2.3 反目标

这些情况即使功能能跑，也算失败：

- 任何未经机器审核或人工处理的内容出现在公开页面。
- 禁钓水域的页面鼓励用户发布「今天还能钓」的内容。
- 用户的 openid、手机号、IP、微信 session_key 出现在接口、日志或后台列表。
- 上传接口可以被匿名调用，或者可以被用来传非图片文件。
- 审核动作没有审核人、时间、原因和审计记录。
- 为了做 UGC 把 V1.0 的浏览、地图、POI 体验弄坏。

## 3. 当前状态与约束

### 3.1 已经有的

- V1.0 staging 已部署，106 个已发布钓点，公开列表、地图、详情、POI 可用。
- 小程序是原生 TypeScript，真实 AppID `wx0d2443850022120f`，已有体验版。
- API 是 NestJS 11 + Prisma + PostgreSQL 18；后台是 Next.js 静态导出 + Ant Design 6。
- `app_user`、`user_identity`、`user_device` 表已存在，但 V1.0 不写入。
- 存储分工作桶和发布桶，桶都是私有的；已有 `StorageAdapter` 的 put、copy、delete、signed URL、getObject。
- 已有 `ClientConfig` 功能开关机制，公开接口 `GET /api/v1/config`，白名单在 `CLIENT_CONFIG_WHITELIST`。
- 已有后台 RBAC，超级管理员、运营、审核员三个角色；审核员目前只有钓点和 POI 只读权限。
- 已有审计日志和后台操作记录模式。
- 已有管理端图片上传，sharp 重编码，10 MB 限制，webp 输出。

### 3.2 还缺的

- C 端登录、用户会话、C 端鉴权 guard。
- `report`、`report_like`、`report_abuse`、`user_session`、图片审核关联表。
- C 端图片上传接口和公开 UGC 图片读取路径。
- 微信 AppSecret、消息推送 token 和 EncodingAESKey、内容安全调用配置。
- 后台内容审核队列与新权限点。
- UGC 的隐私政策、用户协议、社区规范、微信类目与 UGC 声明。
- 静态图片 CDN。当前 `fish-static-staging` 还没有正式 CDN 配置。

### 3.3 约束

| 约束 | 影响 |
| --- | --- |
| 只有 1 名兼职审核，按每日 50 条预估 | 不能做全量先审后发；机审通过即发布，人工抽查 |
| 微信 `msgSecCheck`、`mediaCheckAsync` 有调用成本与配额 | 文本同步检查，图片异步检查；失败不能放行 |
| 图片审核需要腾讯可访问的 URL | 私有工作桶生成不少于 30 分钟的签名 URL |
| 图片 CDN 未就绪 | UGC 已发布图片先走 API 公开读取路径，CDN 就绪后切换 |
| 小程序请求域名、上传域名、下载域名需要单独配置 | 上线前在微信后台补 `fish-api-staging.unihuan.com` |
| 禁钓点有合规风险 | 禁钓点不开放发布，页面隐藏情报区 |
| 管理端 CSP 已限制图片源 | 后台预览待审图片需要放行 OSS 工作桶签名域名，或改为 API 代理 |
| V1.0 仍在内部测试 | M5 实现必须等 V1.0 验收后再开始，不混入当前发布 |

## 4. 方案选择

### 4.1 时机与范围

之前讨论过三种做法：

- A：只做私密反馈，用户提交给运营，不公开。
- B：现在直接做一个公开的钓友圈，抢在 V1.0 稳定前上线。
- C：按 PRD V1.1 M5 做「用户内容与情报」，V1.0 稳定后开发。

用户已选择 C。理由：V1.0 先把 100 个钓点和内部测试跑稳；UGC 涉及审核、合规、登录和后台，提前塞进 V1.0 会拖慢主线。本设计按 C 展开。

### 4.2 数据与内容模型

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 分表 | `comment`、`catch`、`intel` 三张表，各自逻辑 | 类型清晰，但审核、点赞、举报、列表都要写三套 | 不选 |
| 单表 | 一张 `report` 表，`content_type` 区分三类，鱼获字段可空 | 与 PRD 一致，一套审核和互动逻辑；靠 DTO 做类型校验 | 选这个 |
| 只做评论 | 不做鱼获和情报 | 最简单，但丢掉「晒鱼获」和「补钓点信息」两个核心价值 | 不选 |

### 4.3 登录方式

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 匿名设备号 | 本地生成设备 ID，不登录 | 门槛最低，但无法封禁、无法跨设备、无法追责 | 不选 |
| 静默微信登录 | `wx.login` 换 openid，创建用户，发会话令牌，不取头像昵称 | 用户点一下就能发；能封禁；M6 再补个人资料 | 选这个 |
| 完整 M6 登录 | 先做个人中心、头像昵称、收藏足迹 | 范围翻倍，UGC 迟迟上不了 | 不选 |

M5 只做最小登录。默认昵称由系统生成，例如「钓友 A7K2」，头像用本地默认图。M6 再做用户主动设置头像昵称、收藏、足迹。

### 4.4 审核策略

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 全量先审后发 | 所有内容人工通过才展示 | 最安全，但 1 名兼职审核会成为瓶颈，评论区没有即时感 | 不选 |
| 机审后直接发布 | 文本和图片机器通过即展示，人工抽查 | 兼顾安全与体验；需要举报兜底和快速下架 | 选这个 |
| 只做举报后处理 | 先发，没人举报就不管 | 风险太高，不符合微信内容安全要求 | 不选 |

### 4.5 图片读取

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 只走 CDN | 发布桶绑定 `fish-static` 域名 | 最省 API 带宽，但 CDN 未就绪，现在会 404 | 暂不选 |
| API 公开读取 | `GET /api/v1/uploads/public/ugc/{reportId}/{file}` 从发布桶读 | 能立刻用，审核下架后能立即 404；占 API 带宽 | V1.1 先用这个 |
| OSS 公共读 | 发布桶开公共读 | 违反私有桶约束 | 不选 |

CDN 就绪后，公开图片 URL 可以从 API 路径切换到 CDN 路径，数据库和审核流程不变。

## 5. 产品体验

### 5.1 入口与位置

不新增底部 Tab。入口在钓点详情页，位于「注意事项」之后、「周边配套」之前：

```text
┌──────────────────────────────────────┐
│ 钓点标题  [区域] [核心] [开放] [收费]  │
│ 地图预览                              │
│ 基本信息                              │
│ 钓点简介                              │
│ 注意事项                              │
│ 核实时间                              │
│                                      │
│ 钓友情报  12                  [写一条] │
│ [全部] [评论] [鱼获] [情报]           │
│ 阿海 · 2 小时前 · 鱼获                │
│ 今天罗非爆护，巴掌大，钓了十几条。      │
│ [图] [图] [图]                        │
│ 罗非 2.5 kg              ♥ 18  [···]  │
│ ...                                  │
│ [加载更多]                            │
│                                      │
│ 周边配套                              │
└──────────────────────────────────────┘
```

选择这个位置的原因：用户看完钓点基本信息后，最想知道「最近有人去吗、怎么样」；周边配套是下一步行动，放在情报之后更顺。

### 5.2 信息区结构

- 标题：「钓友情报」，右侧显示总数和「写一条」。
- 筛选：`全部`、`评论`、`鱼获`、`情报` 四个 chip，单选，默认全部。
- 列表：按发布时间倒序，首屏 3 条，加载更多每次 10 条。
- 空状态：「还没有钓友情报，来做第一个分享的人。」按钮「写一条」。
- 加载中：3 条骨架卡片，不用全屏转圈。
- 失败：「情报加载失败」+「重试」，不影响钓点主体内容。
- 底部：加载更多；没有更多时显示「已经到底了」。

### 5.3 内容卡片

所有类型共用一张卡片，按类型展示不同信息：

```text
[头像] 昵称 · 2 小时前 · [类型标签]
正文，最多展示 6 行，超出显示「展开」
[图片网格，1 至 6 张，点击预览]
鱼获：鱼种 · 重量
情报：可选「运营已采纳」标记
♥ 18    [举报/删除，放在 ··· 菜单]
```

- 类型标签：`评论` 用中性色，`鱼获` 用强调色，`情报` 用描边色。不超过一个强调色规则，颜色用现有 token。
- 头像：V1.1 默认本地头像；`avatar_url` 为空时显示昵称首字或默认鱼形图标。
- 时间：刚刚、N 分钟前、N 小时前、N 天前，超过 30 天显示日期。
- 图片：1 张时大图，2 至 3 张时两列，4 至 6 张时三列；点击 `wx.previewImage`。
- 点赞：心形图标 + 数量；点击后立即变化，失败回滚并提示。
- `···` 菜单：举报；自己的内容显示删除。举报和删除都需要登录，未登录先登录。
- 不显示用户的 openid、user_id、手机号或精确位置。

### 5.4 发布流程

```text
详情页点「写一条」
-> 未登录：底部登录提示，点「微信登录」
-> wx.login 换会话，不请求头像昵称
-> 进入 pages/report/create?spot_id=...&spot_name=...
-> 选择类型：评论 / 鱼获 / 情报
-> 填写正文（1 至 500 字）
-> 选图（0 至 6 张，相册或相机）
-> 鱼获：选鱼种，填可选重量
-> 勾选「已阅读社区规范」
-> 提交
-> 文本机审通过、无图：立即展示
-> 有图：显示「图片审核中，通过后展示」
-> 机审不通过：提示「内容未通过审核」，不展示
```

发布页字段：

| 字段 | 规则 |
| --- | --- |
| 类型 | 三选一，默认评论；切换时保留正文，清空不适用的鱼获字段 |
| 正文 | 必填，1 至 500 字，去首尾空格；纯文本 |
| 图片 | 可选，最多 6 张；JPG、PNG、WebP；单张不超过 10 MB；前端压缩后上传 |
| 鱼种 | 鱼获类型必填，选项来自 `fish_types` 字典 |
| 重量 | 鱼获类型可选，0.01 至 999.99 kg，最多两位小数 |
| 社区规范 | 首次发布必须勾选；版本和链接来自 `GET /api/v1/config` 的 `legal`，服务端记录用户首次接受的版本与时间 |

发布页底部固定操作栏：`取消`、`发布`。发布中禁用按钮并显示进度；图片逐张上传，全部成功后才创建内容；失败可重试，不产生半条内容。

### 5.5 登录与身份

- 登录动作只发生在用户主动点「写一条」「点赞」「举报」「删除」时。
- 使用 `wx.login` 静默换 code，不调用 `getUserProfile`，不请求头像昵称。
- 登录提示文案：「登录后即可发布情报。我们只获取你的微信身份标识，不会读取你的昵称、头像或手机号。」
- 默认昵称：`钓友` + 用户 ID 后 4 位，例如 `钓友 A7K2`。
- 会话令牌存在小程序本地；access token 失效时自动刷新；刷新失败则重新走微信登录。
- 被封禁用户登录时提示「账号已被限制发布」，不展示具体原因。
- 被限制发布的用户登录后提示恢复日期；有新的驳回通知时，进入详情页前弹一次提示，用户可关闭。

### 5.6 禁钓、暂停、草稿

| 钓点状态 | 情报区 | 发布 |
| --- | --- | --- |
| 已发布、开放 | 展示 | 允许 |
| 已发布、暂停开放 | 展示，顶部提示「该钓点暂停开放，情报会帮助其他人判断」 | 允许 |
| 已发布、禁钓 | 整个情报区隐藏，只保留禁钓提示 | 禁止，接口返回 403 |
| 草稿、已删除、未发布 | 详情页本身不可见 | 禁止 |

禁钓点不允许发布是合规选择。用户可以在其他开放钓点分享；如果钓点后来被解除禁钓，历史情报可以重新展示。

### 5.7 删除与举报

- 删除：仅作者本人；`···` 菜单或「我的内容」页二次确认；软删除，公开页面立即消失，发布桶图片删除；24 小时内清空正文，数据库保留 tombstone 和审计记录。
- 举报：任何登录用户，不能举报自己的内容；原因五选一：广告引流（`ad`）、辱骂攻击（`abuse`）、虚假误导（`false_info`）、隐私侵权（`privacy`）、其他（`other`）；不填自由文本；重复举报按成功处理，不重复计数。
- 举报后文案：「已收到，我们会在 24 小时内处理。」
- 举报不会立刻隐藏内容，避免被恶意举报滥用；运营处理后下架。

### 5.8 文案与命名

- 区块名用「钓友情报」，不用「钓友圈」。V1.1 没有关注和全局流，叫圈会误导。
- 类型名用「评论」「鱼获」「情报」，发布页用一句话解释区别：
  - 评论：分享这次的体验。
  - 鱼获：晒晒今天钓到了什么。
  - 情报：收费、开放、鱼情有变化？告诉钓友。
- 空状态、错误、按钮文案遵循现有小程序的短句风格，不使用夸张词。
- 数字用阿拉伯数字，重量单位用 `kg`，时间用中文相对时间。

### 5.9 明确不做

- 不做评论回复和楼中楼。
- 不做编辑，发布后只能删除重发。
- 新增最小「我的」Tab 和「我的内容」列表，用于查看审核状态、驳回原因和删除；收藏、足迹、头像昵称编辑等 M6 再补。
- 不做周榜和积分。点赞数已经能提供比较；等内容量足够再设计榜单，避免早期被刷。
- 不做实时刷新和下拉刷新，进入详情页时加载。
- 不做到场定位校验和打卡。V1.1 不验证用户是否真的到过现场，靠内容审核和用户自律。

### 6.2 字段说明

- `content_type`：`comment`、`catch`、`intel`。数据库存英文枚举字符串，接口返回英文，客户端映射中文。
- `content`：1 至 500 字纯文本。服务端去首尾空格，拒绝全空白。
- `images`：工作桶 key 数组，最多 6 个，例如 `ugc/{user_id}/{ulid}.webp`。
- `fish_key`：V1.1 的鱼种字典 key，例如 `luofei`。PRD 写的是 `fish_id`，但当前字典是 `key/label` 结构，没有鱼种表；这里用 `fish_key`，不为了一个字段造一张表。若以后鱼种表有独立 ID，再做迁移。
- `catch_weight_kg`：`decimal(5,2)`，最大 999.99，允许空。
- `report_time`：V1.1 等于提交时间，保留给以后「什么时候去的」；本期不单独让用户选。
- `like_count`：冗余计数，和 `report_like` 同事务维护，列表不实时 count。
- `moderation_status`：见第 8 节。
- `machine_result`：只存审核结论、标签、trace_id、错误码，不存图片或用户敏感信息。
- `auditor_id`、`adopted_by`：后台管理员 ID。实现时用命名 relation 指向 `AdminUser`，管理员不允许物理删除。
- `terms_version`、`terms_accepted_at`：首次发布勾选社区规范的版本和时间，用于合规留痕。
- `restricted_until`：限制发布截止时间。到期后自动恢复发布，不需要人工解封；`status=banned` 优先于该字段。
- `app_user.status`：`active`、`banned`、`deleted`；`restricted_until` 不改变 status。
- `report_abuse.status`：`pending`、`removed`、`dismissed`。
- `report_media_check.status`：`pending`、`pass`、`review`、`risky`、`error`、`timeout`、`canceled`。人工已处理的内容，晚到回调置 `canceled`，不改公开状态。
- `ugc_upload.status`：`pending`、`used`、`deleted`。上传记录用于 30 张/天限额、孤儿清理和审计，不扫描桶。
- `rate_limit_counter`：固定窗口计数，key 含动作、主体和窗口；主体 IP 只存 SHA-256，不存原文。
- `images` 存工作桶 key；发布桶 key 用 `ugc/{report_id}/{basename}`，由服务端派生，不重复存。
- `report_time`、`created_at`、`updated_at`、`deleted_at` 全部带时区。
- `Spot` 增加 `reports Report[]` 关系；`AdminUser` 增加 `auditor_reports` 和 `adopted_reports` 两个命名关系。

### 6.3 约束与索引

- `report_like` 复合主键防止重复点赞。
- `report_abuse` 唯一 `(report_id, user_id)` 防止同一用户重复举报同一条内容。
- `report` 的列表索引覆盖「某钓点 + 可见状态 + 时间」；后台队列索引覆盖「状态 + 时间」；用户索引覆盖「我的内容」。
- 外键都 `onDelete: Restrict`，除点赞和举报随内容级联删除；用户和钓点不允许物理删除。
- 不建全文索引。V1.1 内容量小，搜索不是需求。

### 6.4 数据保留

PRD 9.4 要求 UGC 删除后 30 天内彻底清理。V1.1 按更严格的方式处理作者删除：

- 作者删除：立即从公开页面和两个桶移除图片；24 小时内清空 `content`、`images`、`fish_key`、`catch_weight_kg`，保留 `report_id`、`user_id`、`moderation_status=removed`、`reject_reason=author_deleted` 和时间戳作为 tombstone；对应 `ugc_upload` 置 `deleted`。审计日志保留删除动作，不保留正文。
- 被运营驳回或下架的内容行保留，用于审计和重复违规判断；公开接口不返回。正文只给有 `report:read` 的后台人员看。
- 被驳回或下架的工作桶图片保留 30 天供复核，之后删除；数据库只保留 key 和审核结论。
- `ugc_upload` 中 24 小时仍为 `pending` 的记录，删除工作桶对象并把记录置 `deleted`。
- `rate_limit_counter` 过期 24 小时后清理。
- `user_session` 过期或吊销后保留 30 天，之后清理。

## 7. 接口设计

### 7.1 约定

- 全部走现有 `/api/v1`，响应仍用 `{ code, message, data, request_id }`。
- 读接口公开；写接口需要 `Authorization: Bearer <access_token>`。
- 公开列表在带 token 时返回 `liked_by_me` 和 `is_mine`；不带 token 时为 `false`。
- 游标分页：`cursor` 为 `base64(created_at|report_id)`，`limit` 默认 10，最大 20；返回 `next_cursor` 和 `total`。
- 时间统一 ISO 8601；`catch_weight_kg` 按现有 decimal 约定返回字符串，客户端格式化。
- 所有写接口校验 `Content-Type` 和 DTO；正文不接受 HTML。
- 功能开关关闭时，写接口返回 `FEATURE_DISABLED`，公开列表返回空列表；后台审核接口不受影响。

### 7.2 C 端登录

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/wechat/login` | 否 | body `{ code }`，换 openid，创建或查找用户，发令牌 |
| POST | `/api/v1/auth/refresh` | 否 | body `{ refresh_token }`，轮换刷新令牌 |
| POST | `/api/v1/auth/logout` | 是 | body `{ refresh_token }`，吊销当前会话 |
| GET | `/api/v1/auth/me` | 是 | 返回昵称、头像、是否可发布、限制截止时间、最近审核通知 |

登录响应：

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "Bearer",
  "expires_in": 7200,
  "user": {
    "nickname": "钓友 A7K2",
    "avatar_url": null
  }
}
```

规则：

- access token 2 小时，refresh token 30 天，refresh 每次轮换。
- refresh token 只存 SHA-256 哈希；检测到已吊销的 refresh token 被重用时，吊销该用户全部会话并记安全日志。
- access token 和 refresh token 使用独立的 `APP_JWT_ACCESS_SECRET`，不能和后台 JWT 共用。
- 登录时 `jscode2session` 返回的 `session_key` 只在内存中使用，不落库、不写日志。
- 用户被 ban 或 `deleted_at` 非空时，登录和刷新都返回 403；不自动解封。
- 同一 openid 并发首次登录用唯一约束兜底，冲突时重查。
- 登出同时校验 access token 和 refresh token，refresh token 必须属于当前用户；只吊销该会话，不影响其他设备。

`GET /api/v1/auth/me` 响应：

```json
{
  "user": {
    "nickname": "钓友 A7K2",
    "avatar_url": null
  },
  "can_publish": true,
  "restricted_until": null,
  "notices": [
    {
      "report_id": "01J...",
      "moderation_status": "human_rejected",
      "reject_reason": "广告引流",
      "audit_time": "2026-11-20T12:00:00.000Z"
    }
  ]
}
```

- `can_publish` 在 `status=banned`、`restricted_until` 未到期、或 `deleted_at` 非空时为 `false`。
- `notices` 返回最近 30 天、最近 3 条被驳回或下架的内容，不含作者自己删除的内容；小程序用本地记录避免同一条重复弹窗。
- 这是页面提示，不是推送或站内信。

### 7.3 C 端图片上传

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/uploads/ugc` | 是 | multipart `file`，返回工作桶 key |

响应：

```json
{
  "key": "ugc/01J.../01J....webp",
  "width": 1280,
  "height": 960,
  "size_bytes": 182400
}
```

规则：

- 只接受 JPG、PNG、WebP，按文件头判断，不信任扩展名。
- 单张最大 10 MB，最长边 1600 px，webp 质量自适应，目标 300 KB。
- 用 sharp 重新编码，自动旋转，去除 EXIF 和 GPS。
- 每用户每天最多 30 张；按 `ugc_upload` 记录计数，单次内容最多引用 6 张。
- 写入对象前先插入 `ugc_upload` 记录，状态 `pending`；对象写入失败时把记录置 `deleted`，避免无记录孤儿。
- key 前缀必须是 `ugc/{当前用户 ID}/`，不能引用别人的 key。
- 不做公开签名 URL，发布页用本地临时路径预览。

### 7.4 内容接口

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/reports` | 是 | 发布评论、鱼获或情报 |
| GET | `/api/v1/spots/{spot_id}/reports` | 可选 | 某钓点的公开内容，支持类型筛选和游标分页 |
| POST | `/api/v1/reports/{report_id}/like` | 是 | 点赞，幂等 |
| DELETE | `/api/v1/reports/{report_id}/like` | 是 | 取消点赞，幂等 |
| POST | `/api/v1/reports/{report_id}/abuse` | 是 | 举报，重复举报按成功处理 |
| GET | `/api/v1/reports/mine` | 是 | 我的内容，含待审、已发布、驳回、下架；支持状态筛选和游标分页 |
| DELETE | `/api/v1/reports/{report_id}` | 是 | 作者删除自己的内容 |

创建请求：

```json
{
  "spot_id": "01J...",
  "content_type": "catch",
  "content": "今天罗非爆护，巴掌大，钓了十几条。",
  "image_keys": ["ugc/01J.../01J....webp"],
  "fish_key": "luofei",
  "catch_weight_kg": 2.5,
  "terms_version": "2026-11-20"
}
```

创建响应：

```json
{
  "report_id": "01J...",
  "moderation_status": "published",
  "message": "已发布"
}
```

如果机器审核不通过：

```json
{
  "report_id": "01J...",
  "moderation_status": "machine_rejected",
  "message": "内容未通过审核"
}
```

规则：

- `spot_id` 必须是已发布、未删除的钓点；禁钓点返回 403。
- 用户 `status=banned`、`restricted_until` 未到期或 `deleted_at` 非空时返回 403；限制发布只拦发布，不拦浏览、点赞和举报。
- `content` 按 Unicode 字符计数，一个 emoji 算一个；去首尾空格后 1 至 500 字。
- `comment` 不允许 `fish_key` 和 `catch_weight_kg`；`catch` 必须 `fish_key`，重量可选；`intel` 不允许鱼获字段。
- `fish_key` 必须在启用的 `fish_types` 字典里。
- `image_keys` 去重后最多 6 个，每个必须属于当前用户的 `ugc_upload` 记录，状态为 `pending`，且 key 以 `ugc/{当前用户 ID}/` 开头；创建成功后把这些记录置 `used`。
- `terms_version`：用户从未接受社区规范时必须传当前版本，版本值来自 `GET /api/v1/config` 的 `legal.terms_version`，服务端与 `UGC_TERMS_VERSION` 比对后写 `terms_accepted_at` 和 `terms_version`；已接受过的可以省略；未传或版本不符返回 400。
- 创建后返回 201，不管机审结果；客户端根据 `moderation_status` 展示。
- 重复提交不做幂等键，客户端提交时禁用按钮；网络失败由用户决定是否重试。

公开列表项：

```json
{
  "report_id": "01J...",
  "spot_id": "01J...",
  "content_type": "catch",
  "content": "今天罗非爆护，巴掌大，钓了十几条。",
  "images": [
    "/api/v1/uploads/public/ugc/01J.../01J....webp"
  ],
  "fish_key": "luofei",
  "catch_weight_kg": "2.50",
  "created_at": "2026-11-20T10:30:00.000Z",
  "like_count": 18,
  "liked_by_me": false,
  "is_mine": false,
  "is_adopted": false,
  "author": {
    "nickname": "钓友 A7K2",
    "avatar_url": null
  }
}
```

公开列表只返回 `published` 和 `human_approved`，且钓点未删除、未禁钓、已发布。作者信息不返回 user_id。`total` 是当前筛选下的可见总数。`images` 可以返回相对路径，小程序用 `mediaUrl` 补 API origin；服务端不依赖 CDN 域名，CDN 就绪后再切换为绝对 URL。

我的内容：

- `GET /api/v1/reports/mine?status=all|pending|published|rejected|removed&cursor=&limit=`。
- `pending` 对应 `machine_pending`；`published` 对应 `published`、`human_approved`；`rejected` 对应 `machine_rejected`、`human_rejected`；`removed` 对应运营下架，不含作者删除的 tombstone。
- 每项返回 `report_id`、`content_type`、`content`、`images`、`moderation_status`、`reject_reason`、`created_at`、`audit_time`、`spot`（spot_id、spot_name、open_status、是否可打开详情）。
- 待审和被驳回的图片在私有工作桶，接口返回 15 分钟签名 URL，仅作者本人可见；已发布图片返回公开读取路径。
- 钓点被禁钓、下线或删除时，`spot.can_open=false`，列表仍展示内容、状态和删除按钮，点击只提示「钓点当前不可访问」。
- 作者可以在任何非删除状态删除自己的内容；删除后从列表消失。
- 公开接口不返回待审、驳回、下架内容；这个接口只返回当前登录用户自己的内容。

| POST | `/api/v1/admin/abuse-reports/{id}/handle` | `report:moderate` | `action=remove` 或 `dismiss` |
| POST | `/api/v1/admin/users/{id}/restrict` | `user:restrict` | 限制发布 1 至 30 天，必须填原因 |
| DELETE | `/api/v1/admin/users/{id}/restrict` | `user:restrict` | 提前解除限制 |
| POST | `/api/v1/admin/users/{id}/ban` | `user:ban` | 封禁，必须填原因 |
| POST | `/api/v1/admin/users/{id}/unban` | `user:ban` | 解封，不恢复已下架内容 |

队列定义：

| `queue` | 含义 | 包含状态 |
| --- | --- | --- |
| `spot_check` | 机审通过，等人工抽查 | `published` |
| `pending` | 机审待定或图片审核超时 | `machine_pending` |
| `rejected` | 已驳回 | `machine_rejected`、`human_rejected` |
| `removed` | 已下架 | `removed` |

被举报队列由 `/api/v1/admin/abuse-reports` 提供，不放在 `/api/v1/admin/reports` 的 `queue` 里；后台摘要接口会返回举报待处理数用于导航徽标。

后台列表项额外包含：钓点名称、作者 user_id 与状态、作者注册时间、作者历史驳回次数、作者限制截止时间、机器审核摘要、图片预览 URL、举报数、`age_hours`、`sla_overdue`、审核人和时间。待审图片用工作桶 15 分钟签名 URL；已发布图片用公开读取路径。管理端 CSP 需要放行工作桶 OSS 域名，或改走 API 签名预览，二者在实现计划中二选一，优先做 API 签名预览。

审核动作规则：

- `approve`：`published` 直接置 `human_approved`；`machine_pending` 先复制图片到发布桶，再置 `human_approved`；复制失败返回 503，不改变状态。
- `reject`：`published` 和 `machine_pending` 都置 `human_rejected`；已发布图片从发布桶删除；`machine_rejected` 不允许再操作。
- `remove`：`published` 和 `human_approved` 置 `removed`，删除发布桶图片；必须填原因。
- `adopt`：只对 `intel` 且公开可见的内容有效，设置 `adopted_at`、`adopted_by`；公开卡片显示「运营已采纳」，但不自动改钓点数据。
- `restrict`：设置 `restricted_until = now + days`，天数 1 至 30；不删除已发布内容，不吊销会话；用户仍可浏览、点赞、举报；`GET /auth/me` 返回限制截止时间，发布接口返回 403。
- `unrestrict`：清空 `restricted_until`，用户立即恢复发布。
- `ban`：置用户 `status=banned`，清空 `restricted_until`，`token_version` 加一，吊销所有会话，并把该用户所有公开内容置 `removed`，原因 `user_banned`。后台必须二次确认，明确会下架该用户全部内容。
- 所有动作写审计日志：`report.approve`、`report.reject`、`report.remove`、`report.adopt`、`abuse.handle`、`user.restrict`、`user.unrestrict`、`user.ban`、`user.unban`；记录操作人、时间、原因、前后状态，不记录正文全文。

### 7.6 微信图片审核回调

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/wechat/media-check/callback` | 微信签名 | `mediaCheckAsync` 异步结果 |

规则：

- 使用安全模式 + JSON 消息推送。校验 `msg_signature = sha1(sort([token, timestamp, nonce, encrypt]))` 和查询参数里的 `signature`，时间戳偏差超过 10 分钟拒绝。
- 请求体为 JSON `{"Encrypt":"..."}`；用 `WECHAT_MSG_AES_KEY` 做 AES-256-CBC 解密，PKCS#7，IV 为 key 前 16 字节；解密后校验 16 字节随机串、4 字节长度、事件 JSON 和 appid 与 `WECHAT_MINI_APPID` 一致。
- 解密后的 `wxa_media_check` 事件按 `trace_id` 查 `report_media_check`；未知 trace 返回 200 并记日志，不重试。
- 同一 trace 的重复回调幂等，已终态直接返回 200。
- 回调只更新图片检查结果和内容审核状态；人工已处理的内容不再被回调改回公开。
- 成功响应纯文本 `success`。
- 不记录密文、解密后的 openid、token 或 AES key。

### 7.9 限流

| 动作 | 限制 |
| --- | --- |
| 发布内容 | 每用户每天 10 条；注册 24 小时内每天 3 条 |
| 上传图片 | 每用户每天 30 张 |
| 点赞 | 每用户每分钟 60 次 |
| 举报 | 每用户每天 20 次 |
| 登录 | 每 IP 每分钟 20 次；每 openid 每分钟 10 次 |

V1.1 生产按 2 个 API 实例设计，限流不能只放进程内。实现规则：

- 用 Postgres `rate_limit_counter` 做固定窗口计数，`INSERT ... ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` 原子累加；不引入 Redis。
- key 由动作、主体和窗口组成，例如 `login:openid:{id}:202611201200`、`report:user:{id}:20261120`；主体是 IP 时只存 SHA-256，不存原文。
- API 只信任本机 nginx 的代理头，在 `app.factory.ts` 配置 `trust proxy` 为 loopback，并把 nginx 的 `X-Real-IP` 传进来；否则 `req.ip` 是 127.0.0.1，按 IP 限流没有意义。
- 图片审核超时、孤儿图片清理、上传记录清理、限流窗口清理、既有 POI 同步等定时任务，统一用 Postgres advisory lock，保证 2 个实例只有一个执行。
- `rate_limit_counter` 过期 24 小时后清理；计数器写入失败时放行还是拒绝由实现计划决定，默认失败关闭，避免保护失效。
- V1.0 的后台登录限流目前是进程内 Map；V1.1 一并改用同一个 `RateLimitService`，规则保持 5 次/60 秒，避免 2 个 API 实例各自计数。

## 8. 审核状态机与工作流

### 8.1 状态

```text
machine_pending
  ├─ 文本 risky / 图片 risky -> machine_rejected（终态）
  ├─ 文本 pass + 无图 -> published
  ├─ 文本 pass + 图片全部 pass -> published
  ├─ 文本 review / 图片 review / 超时 / 审核服务异常 -> 留在 machine_pending，进人工队列
  ├─ 人工通过 -> human_approved（公开）
  └─ 人工驳回 -> human_rejected（不公开）

published
  ├─ 人工通过 -> human_approved
  ├─ 人工驳回 -> human_rejected
  └─ 举报或运营下架 -> removed

human_approved
  ├─ 举报或运营下架 -> removed
  └─ 作者删除 -> removed（deleted_at）

machine_rejected、human_rejected、removed 为不可逆终态；作者可删除重发。
```

### 8.2 文本审核

- 调微信 `security.msgSecCheck` v2，传 `content`、用户 `openid`、`scene=2`、`version=2`。
- `suggest=pass`：继续。
- `suggest=review`：留在 `machine_pending`，进人工队列。
- `suggest=risky`：`machine_rejected`，不提交图片审核，不展示。
- 接口超时或网络错误：不发布，留在 `machine_pending`，`machine_result` 记错误码，进人工队列。
- 文本审核在创建请求内同步完成，超时 8 秒；超过 8 秒按异常处理，不阻塞用户请求太久。
- 审核结果只存结论、标签、trace_id，不存原始响应全文。

### 8.3 图片审核

- 每张图生成工作桶签名 URL，有效期 30 分钟。
- 调微信 `mediaCheckAsync` v2，传 `media_url`、`media_type=2`、`version=2`、`scene=2`、用户 `openid`。
- 每张图建一条 `report_media_check`，`trace_id` 为主键，状态 `pending`。
- 回调返回 `pass`：该图通过。
- 回调返回 `review`：该图待人工，内容留在 `machine_pending`。
- 回调返回 `risky`：整条内容 `machine_rejected`，不复制任何图片到发布桶。
- 10 分钟未回调：定时任务置 `timeout`，内容留在 `machine_pending` 进人工队列，不自动放行。
- 所有图片 `pass` 且文本 `pass`：复制图片到发布桶，内容置 `published`。
- 文本 `review` 但图片全部 `pass`：图片先复制到发布桶？不。文本未通过前不复制，等人工通过时统一复制，避免未公开内容占用发布桶。
- 回调晚于人工处理：人工已 `human_rejected`、`removed` 或 `human_approved` 的，不再因回调改状态，把该 `report_media_check` 置 `canceled` 并记录结果。

### 8.4 人工抽查

- 所有 `published` 内容进入待抽查队列，24 小时内人工通过或驳回。
- `machine_pending`（文本 review、图片 review、超时、审核服务异常）进入待人工队列，未公开，优先级更高。
- 人工通过是显式覆盖，不要求所有 `mediaCheckAsync` 回调已到终态。后台看到当前图片后即可复制到发布桶并置 `human_approved`；未终态的图片检查置 `canceled`，晚到回调不再改状态。这样图片审核超时不会无限期阻塞人工。
- 复制失败返回 503，状态不变；后台可以重试。
- 人工驳回必须填原因，原因写入 `reject_reason`，同时删除发布桶图片；未终态的图片检查置 `canceled`。
- 人工下架用于已发布内容，原因必填，删除发布桶图片。
- 队列按创建时间升序，超过 24 小时高亮；后台显示超时数量和图片检查未终态数量，但不阻塞通过。
- V1.1 先做单条操作。若每日超过 50 条，再扩展勾选批量通过、统一原因批量驳回；批量操作逐条写审计。

### 8.5 举报

- 举报只针对公开内容；作者不能举报自己的内容。
- 举报记录 `pending`，内容保持可见，避免恶意举报立即下架。
- 后台举报队列按时间排序，24 小时内处理。
- 处理动作：
  - `remove`：内容置 `removed`，删除发布桶图片，同一内容的所有 `pending` 举报置 `removed`。
  - `dismiss`：举报置 `dismissed`，内容保持原状态；如果内容仍在待抽查队列，继续抽查。
- 同一用户重复举报同一条内容，唯一约束兜底，返回成功。
- 举报原因只存枚举，不收自由文本，减少隐私内容进入后台。

### 8.6 封禁

- 封禁是高影响动作，仅超级管理员和运营可用，审核员不可用。
- 封禁时：用户 `status=banned`，`token_version` 加一，所有会话吊销，所有公开内容置 `removed`，原因 `user_banned`。
- 解封：用户 `status=active`，`token_version` 加一；已下架内容不自动恢复。
- 封禁和解封都写审计日志，后台二次确认。

### 8.7 失败与补偿

| 失败 | 处理 |
| --- | --- |
| 微信 access_token 过期 | 刷新一次并重试；仍失败则按审核异常进人工队列 |
| 文本审核超时 | 不发布，进人工队列 |
| 图片审核 API 调用失败 | 该图置 `error`，内容进人工队列，不发布 |
| 图片回调丢失 | 10 分钟定时任务置 `timeout`，进人工队列 |
| 回调重复 | 幂等，已终态直接返回 |
| 发布桶复制失败 | 人工通过接口返回 503，状态不变，可重试 |
| 发布桶删除失败 | 记录告警，内容状态仍置终态，定时任务重试删除 |
| 上传后未创建内容 | 24 小时清理任务删除孤儿图片 |
| 微信服务整体不可用 | 所有新内容进人工队列；后台显示告警，不自动放行 |
| 2 个 API 实例同时跑定时任务 | 定时任务先取 Postgres advisory lock；拿不到锁的实例直接退出 |

### 8.8 违规处理与通知

PRD 6.4 要求「首次驳回并通知，重复违规限制发言，严重违规封禁账号」。V1.1 用最小机制满足：

- 首次驳回：后台驳回时填原因；用户下次打开小程序，`GET /auth/me` 返回最近 30 天最多 3 条驳回或下架通知，小程序用一次性弹窗展示。机器直接拒绝的，在发布页当场提示。
- 重复违规：运营或超级管理员可在后台「限制发言」1 至 30 天，设置 `restricted_until`。限制期间只能浏览、点赞、举报，不能发布；到期自动恢复。限制不解封已有内容，也不吊销登录。
- 严重违规：封禁账号，按 8.6 处理。
- 后台内容行展示作者历史驳回次数和限制截止时间，帮助判断是首次还是重复。
- 通知只在小程序内展示，不做微信订阅消息和推送，避免额外授权与合规成本。
- 作者删除自己的内容不产生违规通知。

## 9. 图片存储与读取

### 9.1 上传

- 入口：`POST /api/v1/uploads/ugc`，C 端鉴权。
- 处理：文件头识别、10 MB 限制、sharp 旋转、缩放、webp 重编码、去 EXIF。
- key：`ugc/{user_id}/{ulid}.webp`，写工作桶。
- 返回 key、宽、高、字节数；不返回签名 URL。

### 9.2 发布

- 内容通过人工或机器审核后，复制到发布桶：`ugc/{report_id}/{basename}`。
- 复制由服务端完成，源 key 来自 `report.images`，目标 key 由 `report_id` 和 basename 派生。
- 复制幂等；重复复制覆盖同名对象。
- 删除时按同一规则删除发布桶对象；工作桶对象保留到保留期结束。

### 9.3 公开读取

- `GET /api/v1/uploads/public/ugc/{report_id}/{file}`。
- 校验内容存在、`deleted_at` 为空、状态为 `published` 或 `human_approved`，钓点已发布且未禁钓。
- 校验 `file` 是该内容图片 basename 之一，防路径穿越。
- 从发布桶读取 `ugc/{report_id}/{file}`，返回 `image/webp`。
- 响应头：`Cache-Control: public, max-age=86400`，`X-Content-Type-Options: nosniff`，`Cross-Origin-Resource-Policy: cross-origin`。
- 下架后新请求 404；已经缓存到客户端的图片可能短时间仍可见，这是可接受的取舍。
- `features.ugc=false` 时该路由也返回 404。回滚开关后已发布图片不继续公开，避免审核故障时内容仍可直读。
- CDN 就绪后，公开 URL 切换到 `https://fish-static.unihuan.com/ugc/{report_id}/{file}`，接口保留兼容。

### 9.4 后台预览

- 待审内容用工作桶 15 分钟签名 URL。
- 管理端 CSP 当前只允许 `fish-static`、`fish-api` 等图片源，需要放行 OSS 工作桶域名，或扩展现有 API 预览接口。
- 优先扩展现有 `GET /api/v1/uploads/preview`：签名由服务端生成，支持从 OSS 工作桶读取；管理端只拿到短时 URL，CSP 不需要放行 OSS 域名，也不把 OSS 签名直接暴露给浏览器。
- 如果时间紧，先在 CSP 加 OSS 工作桶域名，记为临时方案，后续收敛到 API 预览。

### 9.5 安全

- 桶保持私有，不开公共读。
- 只接受图片，拒绝 SVG、GIF、PDF 和伪造扩展名。
- 重新编码，去掉 EXIF、GPS 和潜在脚本。
- 文件大小、像素数、每日张数三重限制。
- 公开读取路径只按 report_id 和 basename 查，不接受任意 key。
- 上传 key 前缀绑定当前用户，创建内容时再次校验。

## 10. 后台审核界面

### 10.1 入口

- 在现有后台单页工作区增加「内容审核」导航项，不新增独立路由。
- 导航项显示待处理总数徽标，数字来自 `GET /admin/reports/summary`。
- 只有 `report:read` 权限可见；审核员、运营、超级管理员都有。

### 10.2 布局

```text
┌ 内容审核 ───────────────────────────────────────────────┐
│ [待抽查 8] [待人工 2] [被举报 1] [已驳回] [已下架]        │
│ 筛选：类型 [全部]  钓点 [输入]  仅看超时 [ ]              │
│ ┌─────────────────────────────────────────────────────┐ │

└─────────────────────────────────────────────────────────┘
```

### 10.3 列表与详情

- 队列 Tab：待抽查、待人工、被举报、已驳回、已下架。
- 筛选：内容类型、钓点名称或 ID、仅看超时。
- 行信息：图片缩略图、作者昵称、钓点、类型、正文摘要、机器审核结论、举报数、创建时间、超时标记。
- 点击行打开右侧详情抽屉：完整正文、全部图片、机器审核详情、作者信息、历史审核记录、举报列表。
- 图片点击可放大；待审图片用短时预览，已发布图片用公开路径。
- 空状态、加载态、错误态沿用后台现有组件。

### 10.4 操作

- 通过：二次确认；待审图片复制成功后置 `human_approved`。
- 驳回：弹窗选原因，必填；原因选项：广告引流、辱骂攻击、虚假误导、隐私侵权、其他；可补 200 字说明。
- 下架：弹窗选原因，必填；用于已公开内容。
- 采纳：仅情报类型；点击后记录运营和时间，公开卡片显示「运营已采纳」。
- 限制发言：仅超级管理员和运营；选择 1 至 30 天并填原因；不删除已有内容。
- 封禁用户：仅超级管理员和运营；二次确认文案明确「将下架该用户全部公开内容并注销其登录状态」。
- 所有动作成功后刷新列表和计数；失败保留弹窗并提示。

### 10.5 权限

| 权限 | 超级管理员 | 运营 | 审核员 |
| --- | --- | --- | --- |
| `report:read` | 是 | 是 | 是 |
| `report:moderate` | 是 | 是 | 是 |
| `user:restrict` | 是 | 是 | 否 |
| `user:ban` | 是 | 是 | 否 |
| 现有钓点与 POI 权限 | 不变 | 不变 | 不变 |

服务端校验，前端隐藏只是辅助。

### 10.6 审计

- 每次通过、驳回、下架、采纳、举报处理、限制、解除限制、封禁、解封都写 `audit_log`。
- 记录：管理员 ID、动作、内容 ID、前后状态、原因、时间、请求 ID。
- 不记录正文全文和图片 URL；需要复核时按 report_id 查。
- 审核记录在详情抽屉可查。

### 11.4 登录与会话

- 新增 `src/session.ts`：读写 access token、refresh token、用户信息；提供 `ensureSession()`、`refreshSession()`、`clearSession()`。
- `ensureSession()`：本地有 token 直接返回；没有则调 `wx.login` 换 code，再调登录接口。
- 请求封装：有 token 时带 `Authorization`；收到 401 先刷新一次，再重放原请求；刷新失败清空会话并提示重新登录。
- 并发 401 只触发一次刷新，其他请求等待同一个 Promise。
- 不在页面里直接操作 token；统一走 session 模块。
- 小程序启动或恢复会话时调 `GET /auth/me`，缓存 `can_publish`、`restricted_until` 和审核通知；`notices` 按 `report_id + moderation_status` 记本地已读，避免重复弹窗。
- 发布页从 `GET /api/v1/config` 的 `legal` 读协议版本和三个链接；点击链接用 `<web-view>` 打开，不在客户端硬编码版本号。

## 12. 安全、隐私、合规

### 12.1 身份与令牌

- C 端 access token 和后台 token 使用不同密钥，不能互用。
- refresh token 只存哈希，轮换，重用即全量吊销。
- access token 校验 `token_version`、用户状态、`deleted_at`。
- `session_key` 不落库、不写日志。
- 小程序本地存储只放 token 和昵称，不放 openid。

### 12.2 数据最小化

- 用户表不存手机号、身份证、真实姓名。
- `user_identity` 只存 openid、unionid；不返回给客户端。
- 会话 IP 可截断存储（IPv4 存前三段，IPv6 存前 48 位）或 HMAC；不存完整 IP 明文。
- 日志不记录正文、图片 URL、token、openid。
- 后台列表不显示 openid；需要排查时按 user_id 查。

### 12.3 内容安全

- 文本和图片都过微信内容安全；失败不放行。
- 人工抽查覆盖所有机审通过内容，24 小时内完成。
- 举报 24 小时内处理；严重违规封禁。
- 上传图片重编码，去除元数据，防伪造文件。
- 禁钓点禁止发布，避免合规风险。
- 用户发布即授予平台非独占展示许可，用于钓点页和钓点信息完善；条款写进用户协议。

### 12.4 合规清单

- 微信小程序类目是否覆盖 UGC，是否需要增加「社交-社区/论坛」类目，上线前向微信和法务确认。
- 隐私政策增加 UGC、相册/相机、内容审核、公开展示、删除方式。
- 用户协议增加内容规范、授权范围、违规处理、免责声明。
- 提供内容删除入口和账号注销入口；注销在 M6 完成，M5 至少提供内容删除。
- 首次驳回通知、重复违规限制发布、严重违规封禁的规则写进用户协议和社区规范。
- 法务页面放在 `https://fish.unihuan.com/legal/terms`、`/legal/privacy`、`/legal/community`；`fish.unihuan.com` 加入小程序业务域名，发布页用 `<web-view>` 打开。社区规范至少覆盖广告引流、辱骂攻击、虚假信息、隐私侵权、禁钓水域、未成年人内容。
- 法务页面和社区规范需要法务或运营确认后再上线，版本号与 `UGC_TERMS_VERSION` 一致。
- 内容审核记录保留，配合监管查询。
- 未成年人保护：不收集年龄；发现未成年人违规内容按平台规则处理。
- 数据出境：不涉及，服务在境内。

### 12.5 审计与保留

- 审核动作全部写审计日志，保留至少 1 年。
- 内容行软删除永久保留；图片按 6.4 保留。
- 安全事件（refresh 重用、批量举报、审核服务异常）写告警日志。
- 后台操作日志与内容审核记录分开，避免审计日志被内容删除影响。

## 15. 已定决策与待确认

### 15.1 本设计已定

- 一张 `report` 表，三种 `content_type`，不做三张表。
- 静默微信登录，默认昵称，M5 不取头像昵称；M6 补个人资料。

- 图片先走 API 公开读取，CDN 就绪后切换。
- 不做全局流、关注、私信、楼中楼、榜单、积分。
- 不做编辑；作者可删除。
- 新增最小「我的」Tab 和「我的内容」列表，显示审核状态、驳回原因，支持删除；收藏、足迹 M6 再补。
- 后台审核员可通过、驳回、下架、采纳；限制发布和封禁仅超级管理员和运营。
- 首次驳回通过 `GET /auth/me` 在小程序内提示；重复违规限制发布 1 至 30 天；严重违规封禁。
- 功能开关 `features.ugc` 默认关闭；关闭时公开列表和 UGC 图片路由都返回空或 404。
- 正文 1 至 500 字，最多 6 图，鱼获重量 0.01 至 999.99 kg。
- 发布每天 10 条，注册 24 小时内 3 条；上传每天 30 张，用 `ugc_upload` 记录计数和孤儿清理。
- 限流使用 Postgres 计数，不引入 Redis；2 个 API 实例共享；定时任务用 advisory lock。
- 人工通过可以覆盖未完成的图片机审，晚到回调置 `canceled`。
- 作者删除后 24 小时内清空正文、图片和鱼获字段，保留 tombstone 和审计日志。
- 24 小时人工抽查和举报处理 SLA；首版单条操作，超过每日 50 条再加批量。

### 15.2 已确认与按推荐收敛

用户已确认：

1. 区块名用「钓友情报」。
2. 含图内容整条等图片审核通过后再展示，不做文本先发、图片后补。
3. 现在加最小「我的」Tab 和「我的内容」列表，用于查看审核状态、驳回原因和删除。
4. 微信 UGC 类目还没确认，先按可做设计；公开上线前必须确认。如果微信不允许，保持 `features.ugc=false`，退回私密反馈方案，不绕过类目限制。

其余按推荐收敛，若批准前不同意可直接改：

- 禁钓点不开放发布，情报区隐藏。
- V1.1 不做周榜、积分、等级。
- M5 用系统默认昵称和默认头像，不做头像昵称编辑；M6 再补。
- 审核员只能通过、驳回、下架、采纳；限制发布和封禁只给运营和超级管理员。
- 24 小时是人工抽查和举报处理目标；如果实际只有你一个人审核，`machine_pending` 可以放宽到 48 小时，已公开内容的抽查不阻塞用户浏览。
- 首版单条审核操作；每日超过 50 条再扩展批量通过和统一原因批量驳回。
- 驳回或下架图片保留 30 天，审计日志保留 1 年；作者删除后 24 小时内清空正文和图片引用。

## 16. 术语

| 术语 | 含义 |
| --- | --- |
| 钓友情报 | 钓点详情页的 UGC 区，包含评论、鱼获、情报 |
| 评论 | 纯文本体验分享，可带图 |
| 鱼获 | 带鱼种和可选重量的晒图内容 |
| 情报 | 现场变化、收费、开放状态、鱼情等信息 |
| 机审 | 微信内容安全文本与图片审核 |
| 抽查 | 对机审通过内容的人工复核 |
| 采纳 | 运营标记某条情报有价值，用于更新钓点 |
| 工作桶 | 私有桶，存待审图片 |
| 发布桶 | 私有桶，存已通过图片，通过 API 或 CDN 读取 |
