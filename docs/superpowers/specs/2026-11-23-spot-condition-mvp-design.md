# 结构化现场情报 MVP 设计稿

- 日期：2026-11-23
- 状态：待评审
- 关联方向：A. 深圳周末钓鱼决策工具
- 目标版本：V1.2 前置切片

## 1. 背景与问题

体验反馈指出：钓点本身是钓鱼人的「命根子」，公开钓点库很容易陷入同质化红海，且信息一旦过期就没有价值。方向 A 不再把产品定位成「钓点大全」，而是回答周末出行前的四个问题：

1. 现在能不能钓
2. 收费有没有变化
3. 人多不多
4. 停车、厕所、餐饮等现场条件是否可用

现有 `report` 已经支持评论、鱼获、情报三种自由文本，但文本难以比较、聚合和判断时效。本切片在现有上报链路上增加**结构化现场情况**，让详情页和列表直接给出可比较、带时间戳的现场结论。

## 2. 目标与非目标

### 目标

- 用户可在 10 秒内提交一条结构化现场情况，不必写长文。
- 钓点详情页展示最近 7 天内最新一条现场情况，并明确标注观察时间和新鲜度。
- 首页列表卡片展示最新现场摘要，让「去哪钓」在列表层就能做初筛。
- 复用现有登录、限流、内容审核、举报和后台审核队列，不新建一套 UGC。
- 结构化字段可被后台筛选和后续统计使用。

### 非目标

- 不做实时水位、潮汐、天气或鱼口预测。
- 不做现场照片必须上传；图片仍为可选。
- 不做积分、排行榜、签到或激励。
- 不做收费钓场认领、预订或 B2B 商家后台。
- 不做独立社区信息流；现场情况不进入公开 UGC 时间线。

## 3. 方案选择

### 方案 A：扩展 `report`（选用）

在 `report` 表增加现场字段，新增 `content_type='condition'`，复用现有上报、审核、限流和后台队列。

- 优点：改动最少，复用内容安全、图片、举报、审核和权限；上线快。
- 缺点：`report` 表字段变多；现场情况与社交内容共用一张表，需要在公开列表层做过滤。

### 方案 B：独立 `spot_condition` 表

- 优点：模型最干净，现场情况与社交内容彻底分离。
- 缺点：需要新的审核队列、权限、限流、举报和后台页面，首版成本明显更高。

### 方案 C：只做运营录入的官方现场

- 优点：信息质量最高，冷启动可控。
- 缺点：无法形成高频更新，回到「人工维护钓点库」的老问题。

**结论**：首版选 A。等现场情况量级和审核流程稳定后，再评估是否拆成独立表。运营官方录入作为后续补充能力，不进入本切片。

## 4. 数据模型

### 4.1 `report` 新增字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `condition_open_status` | varchar(16) null | 否 | `open` / `paused` / `banned`，复用 `OPEN_STATUS` |
| `condition_fee_status` | varchar(16) null | 否 | `free` / `paid` / `member`，与 `fee_status` 字典一致 |
| `condition_crowd_level` | varchar(16) null | 否 | `low` / `medium` / `high` |
| `condition_facilities` | text[] default `{}` | 否 | `toilet` / `parking` / `food` / `water` / `shade` / `rental` |
| `observed_at` | timestamptz null | 否 | 用户观察时间；缺省为提交时间 |

索引：

```text
(spot_id, content_type, moderation_status, observed_at DESC)
```

现有 `(spot_id, moderation_status, created_at)` 保留。

### 4.2 共享枚举

在 `packages/shared/src/enums.ts` 增加：

```ts
export const CONDITION_CROWD_LEVEL = {
  LOW: 'low',
  MEDIUM: 'medium',
  HIGH: 'high',
} as const;

export const CONDITION_FACILITY = {
  TOILET: 'toilet',
  PARKING: 'parking',
  FOOD: 'food',
  WATER: 'water',
  SHADE: 'shade',
  RENTAL: 'rental',
} as const;
```

`open_status` 复用 `OPEN_STATUS`，`fee_status` 复用现有 `fee_status` 字典的键。`REPORT_CONTENT_TYPE` 增加：

```ts
CONDITION: 'condition',
```

### 4.3 校验规则

- `content_type='condition'` 时，至少填写以下之一：开放状态、收费状态、人流、设施。
- `observed_at` 可选；缺省为服务器当前时间。允许最多 5 分钟时钟偏差，最多回溯 24 小时；超出返回 400。
- `condition_facilities` 去重后最多 6 个，每个必须在枚举内。
- `content` 对 `condition` 类型允许为空；为空时跳过文本机审，并在 `machine_result` 记录 `{ "skipped": "structured_only" }`。
- `content` 非空时仍按 1 至 500 个 Unicode 字符校验并走文本机审。
- 图片仍为可选，最多 6 张，走现有上传和图片审核链路。
- 其他内容类型不允许携带 `condition` 字段。

## 5. API

### 5.1 创建现场情况

`POST /api/v1/reports`

```json
{
  "spot_id": "01HX0000000000000000000000",
  "content_type": "condition",
  "content": "",
  "condition": {
    "open_status": "open",
    "fee_status": "free",
    "crowd_level": "low",
    "facilities": ["toilet", "parking"],
    "observed_at": "2026-11-23T10:30:00+08:00"
  }
}
```

响应沿用现有 `report_id`、`moderation_status`、`message`。结构化字段安全，无图且无正文时直接进入 `published`；有图时仍按图片审核状态等待。

### 5.2 详情返回

`GET /api/v1/spots/:id` 增加：

```json
{
  "latest_condition": {
    "open_status": "open",
    "fee_status": "free",
    "crowd_level": "low",
    "facilities": ["toilet", "parking"],
    "observed_at": "2026-11-23T10:30:00+08:00",
    "reported_at": "2026-11-23T10:32:00+08:00",
    "age_hours": 3,
    "freshness": "today",
    "report_count_7d": 3
  }
}
```

- `latest_condition` 只取最近 7 天内、已发布的最新一条；没有则为 `null`。
- `freshness`：`today`（24 小时内）、`recent`（72 小时内）、`stale`（超过 72 小时，仍在 7 天内）。
- `report_count_7d` 用于表达「多少人在报」，不是点赞数。

### 5.3 列表返回

`GET /api/v1/spots` 的每一项增加同样的 `latest_condition` 结构，但省略 `report_count_7d`。实现方式：先查当页 spot_id，再用一次查询按 `spot_id` 取最新一条，避免 N+1。

### 5.4 公开 UGC 列表

公开评论/鱼获/情报列表默认排除 `content_type='condition'`，避免现场情况在时间线里重复出现。后台列表不排除。

## 6. 小程序

### 6.1 详情页

- 在标题和标签下方增加「现场情况」卡片。
- 有数据时显示：开放状态、收费、人流、设施标签、`3 小时前`、`3 人上报`。
- 无数据或超过 7 天：显示「暂无近期现场情况」和「补充现场」按钮。
- 卡片下方保留免责声明：「来自钓友上报，仅供参考，以现场公告为准。」
- 不使用用户昵称或头像，只显示「钓友上报」。

### 6.2 首页列表

- 卡片在现有开放状态、收费标签下增加一行现场摘要：`2 小时前 · 开放 · 人少 · 有停车`。
- 没有现场数据时不占位，不显示假信息。

### 6.3 上报页

- 类型从 3 个增加到 4 个：评论、鱼获、情报、现场。
- 4 个类型改为 2×2 网格，避免单卡过窄。
- 选择「现场」后显示：
  - 开放状态：开放 / 暂停 / 禁钓（可空）
  - 收费：免费 / 收费 / 需会员（可空）
  - 人流：人少 / 一般 / 人多（可空）
  - 设施：厕所 / 停车 / 餐饮 / 补水 / 遮阴 / 租赁（可多选）
  - 观察时间：刚刚 / 1 小时内 / 今天 / 昨天（默认刚刚）
  - 补充说明：选填，0 至 500 字
- 至少选择一项结构化字段才能提交。
- 提交前二次校验，失败时滚动到对应字段。

### 6.4 统一文案

- 「现场」而不是「实时」；避免承诺实时性。
- 「钓友上报」而不是「官方核实」。
- 新鲜度用「刚刚 / X 小时前 / X 天前」，超过 7 天不显示。

## 7. 后台

- 体验反馈之外，复用「钓友情报」审核队列。
- 类型筛选自动出现「现场」。
- 详情展示结构化字段和观察时间，正文为空时显示「仅结构化上报」。
- 审核动作不变：通过、驳回、下架、举报处理。
- 后台列表默认包含现场条目；公开时间线排除。

## 8. 开关与灰度

- 复用 `features.ugc`：现场情况是 `report` 的一种类型，首版不新增开关。
- staging 打开 `features.ugc` 验证；生产默认关闭，按体验名单灰度。
- 若后续要关闭社交 UGC 但保留现场情况，再增加 `features.condition` 拆分；本切片不做。

## 9. 指标

- 每周现场上报数、去重上报人数。
- 有 7 天内现场情况的已发布钓点占比。
- 详情页「现场情况」卡片曝光到导航点击的转化率。
- 现场上报机审驳回率、人工驳回率。
- 上报后 24 小时内被举报或下架的比例。

首版目标：staging 体验组内，30% 的详情页访问能命中 7 天内现场情况。

## 10. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 上报量不足 | 官方开放状态和收费始终展示；无数据时显示补充入口；后续加运营录入 |
| 虚假或过期信息 | 24 小时观察时间限制、7 天展示窗口、新鲜度标签、举报入口 |
| 恶意刷量 | 复用每日上报限流、机审、人工队列和封禁 |
| 隐私 | 现场卡片不展示用户身份，只展示聚合结果 |
| 列表性能 | 一次批量查询 + `(spot_id, content_type, moderation_status, observed_at)` 索引 |

## 11. 测试

### API e2e

- 创建仅结构化、无正文的现场上报，发布成功，详情返回最新值。
- 创建带正文的现场上报，正文走机审。
- 拒绝没有任何结构化字段的上报。
- 拒绝非法枚举、重复设施、未来时间、超过 24 小时的观察时间。
- 7 天前或未发布的现场上报不出现在详情。
- 列表批量返回最新现场摘要，且没有 N+1。
- 公开 UGC 时间线不包含现场条目，后台列表包含。
- `features.ugc=false` 时写接口返回 `FEATURE_DISABLED`。

### 小程序

- 现场类型切换、字段校验、摘要格式化。
- 详情卡片的新鲜度分支：today/recent/stale/empty。
- 首页无数据时不渲染占位。

### Playwright

- 后台按「现场」筛选、查看结构化字段、通过和驳回。

## 12. 实施顺序

1. 共享枚举、Prisma 迁移、Report DTO 扩展。
2. Report 创建校验、空正文跳过机审、后台字段返回。
3. 详情与列表聚合查询，公开时间线排除。
4. 小程序上报页现场类型与字段。
5. 详情卡片与首页摘要。
6. API e2e、小程序单测、Playwright。
7. staging 开关打开，按体验组灰度。

## 13. 待确认

- 观察时间是否允许「昨天」：当前设计允许 24 小时内；如果希望「昨天」也有效，需要放宽到 48 小时。
- 首版是否允许图片：当前沿用现有最多 6 张；如果希望更快审核，可限制为 0 张。
- 现场情况是否显示「3 人上报」：当前显示 7 天内计数；如果担心暴露用户行为，可以只显示最新时间。
- 是否需要运营官方录入：当前不在本切片，作为下一阶段。
